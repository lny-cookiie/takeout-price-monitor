# 自愈闭环说明

这份文档说明「记录原始错误 → 归纳共性问题 → 记录解决方案 → 验证迭代」四步现在各自自动到什么程度、还缺什么、下一步怎么补。它是护城河说明书，不是宣传稿，按真实状态写。

## 一、闭环的四步和现在的实现

### 第一步：记录原始错误（全自动）

每次真机采集失败或异常，系统在保存结果时自动追加一条结构化记录到 `.runtime/knowledge/attempts.jsonl`，字段包括时间、平台、错误码、购物车清理状态、最近八个步骤、运行编号。记录时会自动查询失败模式注册表，给这条记录打上 `fix_id`、`fix_status` 和 `regression_candidate` 标记。这一步不需要人参与，也不会因为记录失败影响采集。

### 第二步：归纳共性问题（半自动）

`scripts/knowledge-registry.ts check` 会按「平台加错误码」聚合出失败签名，算出最近七天的次数和最近出现时间，自动列出三类值得处理的信号：未登记的新失败签名、已登记但再次出现的回退风险、已经修了但还没验证的条目。这一步的聚合和筛选是自动的，但「一句话根因」和「属于哪类问题」仍然要人判断，因为自动推断因果容易得出不可靠的结论。

### 第三步：记录解决方案（半自动）

解决方案登记在 `前期调研/42_失败模式注册表.json`，每条包含编号、现象、根因、修复方式、涉及代码文件、修复提交、状态和验证运行编号。人的失败记录会自动匹配到对应条目；状态是 `verified` 的条目再次出现同错误码时，脚本会报回退风险。登记和更新目前靠人执行命令，还没有做到从代码提交里自动提取。

### 第四步：验证迭代（半自动）

能写成单元测试的判据已经写成测试，例如验证码识别、地址容错、过滤搜索框文字、三标签校验；真机验证通过运行编号记录，用 `npx tsx scripts/knowledge-registry.ts verify F-19 --run <运行编号>` 标注。批次脚本在开跑前自动打印知识库预检，跑完自动在批次目录生成 `failure-digest.md`，把本轮失败和未登记签名留档。回退检测是自动的，但「再跑一组确认修复」目前还需要人触发。

## 二、自动化程度一览

| 环节 | 现在 | 目标 | 差什么 |
| --- | --- | --- | --- |
| 原始错误记录 | 全自动，带修复匹配和回退候选标记 | 保持 | 无 |
| 失败签名聚合 | 全自动 | 保持 | 无 |
| 根因归纳 | 人工判断 | 人加工具辅助 | 需要可靠的特征提取，不建议全自动下结论 |
| 方案登记 | 人工命令 | 提交时自动关联 | 没有从 git 提交和错误码自动生成条目的机制 |
| 单元测试覆盖 | 部分自动 | 每个已验证修复都有测试 | 需要补测试生成和检查 |
| 真机验证标注 | 人工命令 | 修复后自动跑一次单平台并标注 | 没有自动触发和自动判定 |
| 回退检测 | 自动 | 保持 | 需要更细的签名，降低误报 |
| 知识注入执行器 | 没有 | 执行前自动套用已知策略 | 知识目前只影响人，不影响代码路径 |
| 记忆固化 | 半自动：脚本用 `check --memory` 生成四行摘要，由代理写入运行记忆 | 每批结束自动写入 | 脚本不能直接写运行记忆，需要代理执行 |
| 文档数字回填 | 人工 | 脚本按标记自动更新 | 现在靠人改文档，容易滞后 |
| 机制自身的测试 | 已有知识库单元测试 | 覆盖更多签名和回退边界 | 继续补边界用例 |

## 三、命令和文件

- 查看登记：`npx tsx scripts/knowledge-registry.ts list`
- 生成摘要和回退检查：`npx tsx scripts/knowledge-registry.ts check --days=7 --write=进度与实验记录/失败摘要.md`
- 标注真机验证：`npx tsx scripts/knowledge-registry.ts verify F-19 --run 92d12059`
- 生成记忆短句（供每批结束写入运行记忆）：`npx tsx scripts/knowledge-registry.ts check --days=7 --memory`
- 失败记录报表：`npx tsx scripts/knowledge-report.ts --last=20`
- 注册表：`前期调研/42_失败模式注册表.json`
- 人工经验：`前期调研/41_失败与修复知识库.md`
- 自动记录：`.runtime/knowledge/attempts.jsonl`
- 失败归因与优先级：`进度与实验记录/05_失败归因与优化方向_2026-11-19.md`

## 四、还缺什么（按重要性排序）

1. 运行时策略注入还没做。现在知识库只影响人，采集器执行时不会自动套用「这个错误码以前怎么绕过」。下一步是在采集开始时读取注册表，对已知错误码优先使用验证过的备用策略，让修复真正进入代码路径。
2. 修复验证没有闭环。标注验证之后，没有自动重跑一组来证明该错误不再出现；回退检测只是被动地看后续记录。下一步是修复后用单平台跑一组，自动比对结果并调用验证命令。
3. 根因归纳仍然靠人。失败签名可以自动聚合，但「为什么失败」需要结合截图和页面状态判断，自动推断容易把猜测写成事实。这里的正确做法是人加工具，而不是全自动。
4. 记忆写入还是半自动。脚本已经能用 `check --memory` 生成四行摘要，但运行记忆只能由对话代理写入，脚本没有直连权限；下一步是把这个动作写进批次结束流程，由代理执行。
5. 文档数字回填容易滞后。现在实验记录、验收汇总和产品目标库的数字靠人改，批次跑得快时会落后。下一步是用固定标记加脚本回填，避免人工遗漏。
6. 没有定时体检。建议加一个每天固定时间跑的摘要任务，把未登记签名和回退风险推到当天的第一屏。

## 五、为什么这算护城河

代码会被抄，页面会改版，但「每次失败都变成一条可检索、可验证、可回退的经验」这个循环需要长期真机积累和工程纪律，复制成本高。现在的状态是半自动自愈：记录和检测已经自动，归纳、验证和注入还需要人。把上面四点补齐之后，才算真正的自动自愈机制。

Use case: infographic-diagram
制作一张中文技术流程路线图，供产品负责人和工程师共同阅读。画面横向，约3:2，高分辨率，白底、深蓝正文、青蓝业务标签、紫色技术标签、浅灰边框，精致专业的信息图。没有大标题，没有插画，没有水印。中文准确清晰，不要省略指定文字。强调业务和技术在每个节点一一对应，不要分成两张图。
画面主体为8张等宽卡片，第一排01、02、03、04从左往右，第二排05、06、07、08从左往右。第一排用清楚的箭头连接，04从右边外沿折回第二排05，折线经过两排之间空隙、不穿过卡片。第二排箭头从左往右。卡片内分“业务”浅青区和“技术”浅紫区，编号与节点名在顶部。每个文字行要完整，留足空白。底部设3个并排运行保障卡片，之后一条很小的架构与目标注记。主体占78%高度，保障区18%，注记4%。不添加大标题。
8个节点的准确文字如下，允许自动换行，必须保持逻辑：
01 登记监测范围
业务：BD保存城市、区县、品牌和完整分店名
业务：选择配送点位、账号资格、餐期
技术：HTTP接口校验输入；保存门店与场景版本
技术：登记平台入口、用途和动作边界

02 生成与调度任务
业务：一键发起或按餐期自动采集
业务：京东、美团、淘宝闪购进入同一比较批次
技术：Node.js + TypeScript 调度器
技术：三平台独立适配器，共用采集契约
技术：多设备并行；同设备、同账号互斥

03 确认同一实体门店
业务：先按品牌找店，再核对分店与营业地址
业务：复用已确认门店；歧义交人工核实
技术：Midscene + ADB 操作 Android 页面
技术：多模态模型识别候选；程序检查地址与状态
技术：保存门店映射及页面证据

04 三平台分别选品
业务：京东 / 美团 / 淘宝闪购各选销量前五单品
业务：合并候选，任一平台入榜即可进入采价池
技术：完整扫描菜单或读取已核验的全店销量榜
技术：读取详情规格；排除套餐和规格未知商品
技术：保存销量口径、覆盖范围与入选依据

05 核对跨平台同款
业务：逐项确认同店、同品、同规格、同选项
业务：首次确认后复用；证据变化时重新核对
技术：模型推荐匹配 → 程序硬约束 → 人工确认
技术：标准商品映射到三平台商品，保存映射版本
技术：某平台同款未入榜，仍采该平台报价

06 读取单份结算报价
业务：每款按一份，记录展示价与结算应付
业务：同时记录配送、包装、优惠及可售状态
技术：三平台适配器 → Midscene + ADB
技术：选择规格 → 加购 → 结算读价 → 恢复本任务改动
技术：截图脱敏后由模型提取；不下单、不支付

07 校验与证据入库
业务：每笔价格可核对来源、条件、时间与截图
业务：未知、售罄、受限、失败分别展示
技术：Schema校验；金额存整数分；未知保留null
技术：明细完整才验算；错误记录隔离
技术：SQLite保存观测与尝试；证据文件关联哈希

08 同条件比价与展示
业务：展示京东对两家竞对的价差及证据
业务：三方均可比时显示三平台最低价
技术：核验店品、数量、点位、资格、履约及券条件
技术：同批次观察时差≤5分钟；超过15分钟标历史
技术：比较服务输出工作台与CSV；不可比说明原因

底部三个保障卡片每个也明确业务与技术对应：
质量可控
业务：价格正确、同款可比、证据可追溯
技术：独立人工抽检；错价退出比较；更正保留历史
指标：正确率 / 字段覆盖率 / 可比率

稳定可控
业务：异常可定位，已有结果不丢失
技术：状态等待与超时；网络故障有限重试
技术：访问受限即停止；改版复验后启用
指标：有效报价率 / 失败分类 / 恢复用时

效率可控
业务：按时交付，控制每条有效报价成本
技术：复用已验证流程与映射；每轮读取新证据
技术：记录排队、执行、模型调用与人工用时
指标：采集耗时 / 人工介入率 / 单条有效报价成本

三个保障卡片由一条淡灰色横向线连接至主流程，表示贯穿全过程，不用复杂交叉箭头。失败任务也计入统计分母，在底部保障区下方以清晰小字写“统计包含全部计划及失败任务，避免只看成功样本”。

最底部小字两行：
“技术底座：Node.js · TypeScript · SQLite · Midscene · ADB · 多模态模型｜Playwright：自有页面回归验证”
“目标态示意：三平台入口使用条件已满足；展示完整落地流程，不代表当前已完成验收。”

约束：保留现有单进程本地架构，不添加Kafka、Redis、微服务、云集群、爬虫代理池或未经依据的接口。不承诺虚构的99%或秒级性能数字。无UE、无补贴自动决策。图上不出现提示词元信息。

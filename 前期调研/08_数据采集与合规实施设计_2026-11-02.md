# 三平台竞争比价：数据采集与合规实施设计

> 2026-11-04 归档提示。本篇保留历史研究及其当时的假设。当前范围与开发约束以 [项目规范](../agent.md)、[数据治理表](../数据治理/数据治理表.md) 和 [当前采集路线](11_零外部资源下的数据采集路线_2026-11-04.md) 为准。

日期：2026-11-02。服务对象：平台运营团队；优化对象：平台出资的补贴。

> 2026-11-03 已核实美团用户协议与淘宝闪购对第三方智能体的访问规则。长期手机和浏览器自动采价应参照[平台级 AI 自动采价专项](10_AI自动采价的证据与成本_2026-11-03.md)。本篇的人工观察流程及成本仅用于小样本验证。

配套主方案：[独立复审与新版 SaaS 方案](D:/vibecoding/takeout_price_competition/前期调研/07_独立复审与新版SaaS方案_2026-11-02.md)。

## 一页读懂

**推荐路线：先接客户已经有权使用的数据，再为具体决策补采少量价格。暂不自建消费端自动采集体系。**

平台自己的成本和订单决定能否计算补贴效果；竞对的结算页报价用于提供竞争证据。两类数据不能互相替代。

第一版的参与者依次完成：客户交付内部字段与来源说明 → 数据负责人核对范围 → 导入并质检 → 对缺口安排获准观测 → 生成可复核证据 → 批准小范围实验。

这一版做字段治理、授权核验、低频采样、证据比对和失效处理；不做绕过技术限制、借用员工账号、接管消费者登录或把 ERP 数据直接卖给另一平台。

成功标准不是“抓到了”，而是同一条数据同时满足：**有取得与使用依据、场景能解释、价格有证据、仍在有效期内、能支持具体动作。**

已完成公开接口路径和法律依据核查；未完成真实接口准入、合同审核、真人采样、供应商验收及最终法律适用判断。下文的流程、数量、时效都是设计建议。

## 1. 首先把“拿什么数据”拆清楚

| 数据 | 最有价值的来源 | 能回答什么 | 不能直接回答什么 |
|---|---|---|---|
| 本平台菜单、活动配置 | 客户内部系统或经授权的商家系统 | 当前商品和活动是什么 | 用户最终实际看到了什么 |
| 本平台报价日志 | 客户获准提供的报价系统记录 | 某场景下展示的最终应付 | 是否成交、是否退款 |
| 本平台订单及财务分摊 | 客户订单、结算和财务系统 | 实际出资、收入、退款与已核销费用 | 不加补时用户会不会下单 |
| 本平台实验分组与结果 | 客户实验平台；优先导出必要汇总 | 策略是否带来增量、代价多大 | 竞对未来会如何响应 |
| 竞对结算页报价 | 经审查的客户已有观测、面板或供应商 | 某用户在某时刻可见的应付金额 | 所有人都能拿到的价格、真实成交、完整补贴出资 |
| 竞对公开菜单或活动信息 | 允许该用途的公开来源或授权接口 | 商品存在、活动规则、公开价线索 | 隐藏券、支付优惠和用户个性化报价 |
| 竞对商家后台数据 | 商家与平台相关协议允许的授权路径 | 授权店铺可开放的经营字段 | 天然可以向竞争平台披露、所有消费者报价 |

用户看到“平台红包 5 元”，不代表该平台真实支出就是 5 元。它可能涉及共同出资、返还、抵扣、会员或支付机构补助。竞对出资无法核实就保留未知；本平台出资必须用财务口径确认。

## 2. 三平台官方数据接入：已确认与未确认

### 2.1 美团

**已确认**：技术服务合作中心的能力目录列有外卖订单、菜品、门店等能力，并存在商家授权体系。官方技术文章也介绍了服务商通过 API 为商家管理订单的模式。[能力目录](https://developer.meituan.com/ability-center/list)、[官方 SDK 技术介绍](https://tech.meituan.com/2023/01/05/openplatform-sdk-auto-generate.html)。

**未确认**：本项目是否能获准入驻；具体接口是否提供所需费用分摊；是否允许加工后向竞争平台输出。公开协议包含保密及用途限制，实际签署版本和业务范围必须核对。[在线服务协议](https://developer.meituan.com/docs/biz/biz_xn202005112_fcc4ce53-cb41-4491-9680-60257670f5f0)、[商家授权协议](https://open-erp.meituan.com/general/protocol)。

**产品判断**：可以把该路径列为待评估接口，不能直接宣称已解决京东竞对数据来源。

### 2.2 淘宝闪购

**已确认**：现行服务商门户展示选择场景、资质审核、签署协议和保证金等入驻环节；2026-02-05 更新的特权接口文档列出了部分接口的申请条件。金融、生意参谋、CRM 等能力并非注册后自动开放。[服务商门户](https://open.shop.ele.me/)、[特权接口申请](https://open.shop.ele.me/openapi/documents/privilegeapi)。

**未确认**：普通订单接口实际包含哪些字段、补贴分摊是否完整、具体业务场景能否申请、竞争分析用途是否允许。历史饿了么接入指南可证明曾有指定商家授权模式，但不能把 2017 年手册的时效和能力当成当前承诺。[历史接入指南](https://open.shop.ele.me/static/files/join-eleme-openapi.pdf)。

**产品判断**：先核对当前餐饮业务的接口清单和签署协议。淘宝入口和闪购 App 入口也应分别标记；同属一个平台不代表同一入口下报价相同。

### 2.3 京东

**已确认**：京东秒送公开说明商家可自研接入或授权开发者接入；接入说明涵盖商品、促销、订单和结算同步。原门户提示迁往 open.jd.com，计划于 2026 年第四季度下线旧平台。[授权流程及迁移提示](https://opendj.jd.com/index.html)、[对接须知](https://opendj.jd.com/staticnew/widgets/doc/needknow.html)。

**未确认**：上述通用秒送能力是否覆盖本次指定餐饮外卖业务、平台内部全部补贴账、实验与用户分层字段。不能把即时零售接口与餐饮补贴接口混用，也不能根据“计划下线”认定旧接口已经全部不可用。

**产品判断**：对于京东平台客户，优先请其数据负责人从内部提供获准字段；不要绕到商家账号去推算京东平台自己的账。

### 2.4 接口试接前必须交付的验证表

| 核验项 | 合格证据 |
|---|---|
| 业务范围 | 当前餐饮场景名称、接口清单、申请主体与审批结果 |
| 授权对象 | 哪些商家/门店、哪些字段、只读还是写入 |
| 数据用途 | 是否允许本软件处理、是否允许向指定平台客户展示、是否允许派生分析 |
| 账目口径 | 平台出资、商家出资、支付机构出资、退款冲正等字段说明 |
| 可用性 | 测试环境或获准样本响应、更新延迟、限额、费用、撤销机制 |
| 数据责任 | 委托处理协议、个人信息处理角色、保留期、转委托条件 |

“某个接口有 total 字段”“服务商有营业执照”“数据来自商家”均不足以单独通过验收。

## 3. 为什么不建议第一版做自动采集农场

### 3.1 需求量被维度放大

用原方案中的规模作一个说明性计算：20 家哨兵店 × 每店 20 个商品组合 × 每天 48 轮 × 2 家竞对 × 4 种账号场景 = **每天 153,600 个单平台报价观测单元**。这还没有乘多个地址与入口。

这不是对原方案实际请求量的测量；若合并页面、减少组合或做抽样，量会下降。但它说明“20 家店很小”并不成立。尤其菜单展示能同屏读取多个商品，结算报价却取决于购物篮，不能直接用菜单页抓取成本估算。

### 3.2 机器也无法凭空拥有真实用户资格

新客是资格状态，使用后会变化；会员权益可能有次数、余额、到期和券包成本；账号的历史还可能影响可用优惠。合成几个“新客/会员账号”不能代表真实用户分布。

AI 操作浏览器不会增加数据使用权，也不会消除登录、设备、位置与行为带来的偏差。出现限制后，应停止相关路径并核实许可，不能以更换账号或网络作为常规续采机制。

### 3.3 只有满足三个条件才考虑新增自动采集

1. 获得适合当前取得方式、频率和用途的许可或充分法律依据。
2. 获准环境能稳定获得所需场景字段，不依靠规避技术措施。
3. 端到端有效观测成本低于已有方式，并且更快更新确实能改变动作。

当前研究没有取得上述验证结果，因此不把消费端 RPA、云手机或浏览器 Agent 写入第一版必需架构。

## 4. 真人观测如何具体实施

**前提**：客户和执行方已完成研究方案、平台协议及数据用途审查。参与者主动上传，只解决个人参与与部分个人信息处理问题；不能自动消除平台的数据权益或合同限制。

### 4.1 一次任务的定义

一次任务是“同一参与者，在一个收货点和一个短时间窗口，为同一份餐食记录三平台报价”。它产生三条单平台观测，组成一个配对组。

没有三平台对应账号、门店未营业、无法配送或商品缺货时，允许部分完成并记录原因。未完成不是零价，不能硬凑成三平台比较。

### 4.2 任务流程

1. **明确用途**：展示研究目的、接收方范围、采集字段、保存方式、报酬规则及退出入口；不预勾选同意。
2. **确认资格**：参与者自行说明在每个平台的新老状态、会员状态和本次券资格；只记录本任务需要的字段，不索取账号密码、Cookie 或短信验证码。
3. **下发清单**：给出门店、商品、规格、数量、收货点与时间要求。平台顺序做轮换，降低固定先后顺序与短时变化混淆。
4. **正常查看**：参与者本人在 App 选择正确商品，停留在结算页。无需真实支付，也不为研究制造虚假交易或反复取消订单。
5. **截图和最小化处理**：提交能证明商品、门店、费用与应付金额的必要画面；上传前在设备端遮盖姓名、电话、家庭详细地址、账号标识及订单号。不可只在后台前端隐藏。
6. **确认上下文**：记录报价时间、入口、是否更换券、是否需要额外付费权益、可售与预计送达状态；用户确认结构化结果。
7. **复核与入库**：核对商品组合、场景、金额和证据；不合格的说明缺失原因，不要求参与者为通过而改变真实身份或购买会员。

精确收货点会影响配送费，但并不因此需要采集参与者完整家庭地址。优先选择双方获准使用的固定办公楼等测试收货点，以 point_id 关联；私人地址场景尽量只在客户或参与者侧保留必要定位信息。不能核实时标为“参与者声明”，不得显示为已经独立核验。

### 4.3 第一轮不要同时测全部人群

先选择可招募、定义清楚的一种常见场景，例如“各平台老客、无新增付费权益、固定商品组合”。如果参与者拥有会员，就如实记录并归入对应视角，不要求伪装成非会员。

之后再按业务问题安排会员专题、新客专题和夜宵专题。新客不能靠反复注册或购买账号来制造。招募不到某类样本，就报告该层暂缺。

首轮 20 次任务用于发现流程问题；10 店每店 2 个商品组合、每周各 2 次观测用于低频跟踪。这样的密度不支持每店每人群每日分布估计，只能提供具体证据和候选线索。

### 4.4 质量控制要能识别“看起来真实”

| 检查 | 能发现什么 | 仍然不能证明什么 |
|---|---|---|
| 文件哈希和近似图像去重 | 重复上传、部分重复图片 | 图片没被编辑、价格仍有效 |
| 门店与商品明细核对 | 选错店、规格或数量 | 所有隐藏规则均已掌握 |
| 设备上显示时间、用户记录时间与服务器接收时间并存 | 明显过期或时间矛盾 | 截图自带时间一定可信 |
| 已知金额重算 | 抄错金额、重复扣减 | 未展开费用或隐藏券的内容 |
| 少量独立重新观测 | 部分数据造假和已失效活动 | 个性化价格应该完全相同 |
| 人工复核关键建议证据 | 大多数明显场景错配 | 全体用户代表性 |

不要因为与其他人看到的价格不同就判作弊。个性化权益不同，可能正是研究要观察的事实。

对重复参与者，在获准范围内使用随机化的参与者编号，用于统计相关性和处理撤回请求；它仍可能属于可关联的个人信息，不应称为彻底匿名数据。

## 5. 数据结构：缺失必须与零分开

以下是字段设计，不是已经可从三平台获得的字段清单。

### 5.1 来源授权表

| 字段 | 含义 |
|---|---|
| tenant_id / source_id | 客户与数据来源 |
| acquisition_method | 内部导出、授权接口、研究提交、许可供应商等 |
| rights_basis_ref | 对应合同、授权、研究告知或法律评估记录 |
| allowed_purpose / allowed_recipient | 允许做什么、给谁看；不能只写“分析用途” |
| permitted_fields / retention_until | 可处理字段与保存期限 |
| approval_status / revoked_at | 待核验、准入、暂停、撤销 |
| processor_chain | 原处理者、受托方及获准的模型/云服务等转委托方 |

不能把一份笼统的合同复制到所有客户。客户 A 可以看到的数据不自动授权给客户 B。

### 5.2 报价观测表

| 字段组 | 必需内容 |
|---|---|
| 主键与证据 | observation_id、pair_id、source_id、证据位置、文件哈希 |
| 商家 | 平台门店 ID、统一线下门店 ID、匹配确认者与有效版本 |
| 商品组合 | basket_id、每个商品名称、规格、数量、加料/替换、组合版本 |
| 场景 | point_id、平台入口、配送模式、观测时间、用户状态与权益说明 |
| 价格类型 | 展示价/结算页报价/实际支付，不混在一个 final_price 字段里 |
| 金额 | 应付、商品小计、打包、配送、服务费、已展示优惠；金额用整数分 |
| 优惠 | 页面原始优惠名称、适用条件、是否已领、是否已选、次数限制、额外取得成本 |
| 可达性 | 能否购买、库存、配送范围、预计送达、失败原因 |
| 质量 | 抽取待核验/已核验、精确同款/近似/不可比、上下文完整性 |
| 时效 | evidence_captured_at、received_at、known_offer_end、刷新状态 |

优惠“展示类型”与“资金出资方”分别记录。会员券和平台券可能是同一项权益的不同标签，不能重复扣除。

### 5.3 本平台财务与实验表

首期优先由客户在内部按实验组或场景汇总，减少个人信息流转。必要字段包括：符合资格的用户或实验单位数、分配策略、完成订单、退款、平台收入、相关变动成本、平台实际出资、商家及其他方出资、活动和实验 ID、核算日期及冲正状态。

如需曝光或转化，分母应在策略影响发生前定义。仅对已经下单者统计“每单补贴”会漏掉没有下单的人，不能独立证明转化改善。若客户只提供汇总，须同时提供正确推断需要的随机化单位、样本量、方差或其他充分统计量；只有组均值时，不自动生成显著性结论。

订单成本缺失时填 unknown；真实零补贴才填 0。原 Demo 将缺失的 platform_subsidy_cost 转为 0，只适合其模拟输入约定，不能直接接生产数据。

### 5.4 六类信息永远分栏

**观测事实、规则计算、统计估计、业务假设、法律/合同准入状态、动作批准状态。**

例如，截图显示 18 元是观测；两平台相差 2 元是计算；用户愿意为快 10 分钟多付多少钱是估计；“应该减补 1 元”是建议。建议不能用同一个 confidence 字段掩盖其依赖的多种不确定性。

## 6. 计算和样本统计的边界

### 6.1 优先核对报价，不先建完整模拟器

第一版把“支付前应付”作为原始事实，核对可见组成部分。无法解释的残差单列为“未展开或未知金额”。

只有明确知道规则与适用资格时，才进行规则计算；不使用一个固定优惠顺序覆盖三平台。满减的计价基础、配送费能否抵扣、会员券与红包是否互斥，都以实际版本规则为准。

不把商品、配送、会员等展示差额直接称为责任归因。分解可以解释账面价差，无法自动证明哪方出资、为什么用户不下单。

### 6.2 比价分母必须公开

报告显示计划任务数、完成单平台观测数、有效三平台配对数、独立参与者数、覆盖门店数及各类失败原因。

“80% 的样本更便宜”必须附上有效样本定义；不能省略失败和不可比样本。如果低价活动更难访问，缺失可能有方向性，删除缺失后直接计算均价会产生偏差。

样本足够时才能给价格分布或区间，并按参与者、门店、日期等相关结构处理不确定性。样本太少时展示逐条观测和范围，明确不代表总体；不能给少量截图套上精确的置信区间制造可信感。

### 6.3 本平台实际成交不能“校正出”竞对真实价格

本平台账目可以验证本平台金额解析和成本口径，不能直接校正竞对的账号偏差。竞对缺失券、样本选取和风控差异都可能改变价格机制。

只有同一竞对、同场景的适当重叠样本，才可能支持局部偏差估计，而且仍需可迁移性假设。第一版不建设一个全平台通用的偏差修正数。

## 7. 合规：逐项审查，而不是写一句“来源合法”

### 7.1 采集方式与平台数据权益

现行《反不正当竞争法》第十三条涉及以欺诈、胁迫、避开或破坏技术管理措施等不正当方式获取、使用其他经营者合法持有的数据。公开可见、没有采个人信息或低频访问，均不能单独证明一项商业采集合法。[北大法宝核验文本](https://pkulaw.com/chl/1d79285621ad7295bdfb.html)。

最高法发布的 2025 年知识产权典型案例摘要包含电商数据取得与商业利用案件，涉及通过比价插件获取 Cookie、突破反爬保护并收费提供数据服务。该案提示需要看取得方式与使用方式的整体；不能概括为“所有公开数据采集均违法”。本次使用公开案例摘要，未取得案件完整裁判文书。[最高法知识产权法庭案例摘要](https://ipc.court.gov.cn/zh-cn/news/view-5630.html)。

### 7.2 用户与商家授权不是万能授权

参与者可能有权分享自己的某些信息，商家可能有权导出部分经营数据。但他们能授权的范围受实际权利、平台合同和他人信息限制。三方身份都要分清：谁提交、谁有权授权该用途、谁最终收到结果。

对平台客户尤其需要核对“竞争分析与客户交付”是否在许可内。仅允许商家自用经营分析的接口，不应默认用于支持另一家平台的补贴策略。匿名化、数据聚合和报告形式也不会自动扩大合同许可。

### 7.3 个人信息处理

《个人信息保护法》要求目的明确、最小必要，并规定受托处理、自动化决策、敏感信息、跨境与影响评估等要求。具体义务取决于实际处理角色和数据流；本项目不能以用户点了同意或签了供应商合同替代分析。[网信办公布的法律正文](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)、[第二十一条核验](https://pkulaw.com/chl/d653ed619d0961c0bdfb.html)。

建议措施：原图上传前脱敏；平台内部用户分层尽量在客户侧完成；SaaS 不接收电话、账号凭证或家庭详细地址。对仍可关联到参与者的资料设置删除与撤回流程。模型和云服务按实际转委托关系纳入审批，不默认用客户原始资料训练模型或发送境外服务。

原始证据可先提出 30 天的最短业务必要保存方案，但最终期限需根据研究用途、争议处理和适用义务确定。授权、影响评估、操作审计等记录与原图分别管理；不机械规定所有资料一律保存六个月。

### 7.4 补贴和价格行为

《互联网平台价格行为规则》于 2026-04-10 施行。第五条约束对商家自主定价的不合理限制，包括强制或变相强制跟价、降价和开通相关系统；第十五条涉及消费者不知情时同等交易条件下的差别价格问题。[官方规则全文](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/jjjzs/art/2025/art_eef66659c9624c5091bd3acd050b1710.html)。

因此，第一版不执行自动调价是产品风险控制选择，不能把它写成“法律一律禁止自动调价”。平台自主预算调整、已承诺券的履行、商家自愿活动和强制商家承担成本，应分别分析；也不能认为有商家点击同意就一定没有变相强制。

关于《外卖平台补贴行为规范十条》，截至本次检索已确认的官方发布是 2026-06-17 的征求意见稿，未核验到正式生效文本。本文将其作为监管方向，不作为已经生效的新义务。[官方征求意见公告](https://www.samr.gov.cn/hd/zjdc/art/2026/art_53279f84120f4f2ab7dee21fda2c4bd2.html)。

### 7.5 多客户 SaaS 的竞争信息隔离

若未来同时服务美团、淘宝闪购和京东，不能把三家的未公开预算、策略、用户名单或未来活动混进共享模型或共享看板。汇总也不是自动免责条件，小样本汇总可能暴露单个客户策略。

2026 年《互联网平台反垄断合规指引》明确提示竞争性敏感信息交流与算法协调风险。产品默认按客户隔离数据、检索、缓存、模型上下文和导出；跨客户行业基准若有真实需求，应作为独立用途重新评估，而不是默认增值功能。[官方指引](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fldzfys/art/2026/art_ad10c5301fcb426cb839153ca9f5a274.html)。

### 7.6 软件部署本身的义务

境内上线时还需结合实际服务形态核对网站/应用备案、网络安全等级保护、个人信息和生成式 AI 相关要求；不能因为使用了已备案模型就认定 SaaS 自身义务全部完成。当前尚无确定部署方案，因此不在本次方案中编造证照清单、办理时长或固定费用。

原材料提到的在职或实习关系只是历史描述，本次未确认现状。若仍有保密、兼职或竞业方面的合同约束，由签约主体核对实际合同；这次研究没有使用任何雇主内部资料，也不把历史身份当成当前事实。

## 8. 各条数据路径的产品准入判断

| 路径 | 相对可行性 | 必须满足的条件 | 首期处理 |
|---|---|---|---|
| 客户自有平台成本、订单与实验汇总 | 最高，仍需授权 | 字段必要、口径明确、受托处理范围清楚 | 必需 |
| 客户已有竞对观测 | 取决于原来源 | 来源可追溯，合同包含当前处理与交付用途 | 优先核验 |
| 真人主动提交 | 可小规模研究，非天然无风险 | 告知与参与依据、最小化、平台及竞争权益评估、用途限制 | 获准后补缺口 |
| 商家授权 API/ERP | 技术路径存在，用途不确定 | 平台接口许可、商家权限、个人信息依据、允许目标客户用途 | 不直接导入竞对平台 |
| 第三方数据许可 | 取决于证据与合同 | 取得方式审计、允许派生分析和客户交付、稳定性验收 | 有条件采购 |
| 公开网页商业采集 | 逐案判断 | 页面性质、协议、技术措施、频率和使用影响可论证 | 非第一版依赖 |
| 提取 Cookie、伪造身份、绕过限制、批量账号 | 不符合本产品设计目标 | 本方案不建设此类路径 | 排除 |

“相对可行性”是本项目工程和产品判断，不是法律安全等级或最终法律意见。正式启动前，需要针对实际来源和合同完成审核；当前没有需要用户立即授权的外部采集或付费行为。

## 9. 数据供应商验收：买有效观测，不买空泛覆盖

本次没有验证任何供应商能稳定、合法提供三平台指定用户场景的结算报价。原文提到的鼎点、博晓通只能作为待核查线索，不作为推荐名单或授权能力背书。

### 9.1 入围材料

要求候选方针对本任务交付：

- 指定餐饮外卖业务的覆盖说明，避免用京东电商、即时零售或历史饿了么案例替代。
- 采集方式、数据来源主体、是否使用登录或技术规避、原始证据与授权链说明。
- 允许交付给哪类客户、是否允许竞争分析、派生结果、SaaS 展示及转委托。
- 按场景、门店、商品、时效区分的服务能力；不是只有“支持 API”四个字。
- 对缺货、不可达、失败、过期、错误的定义，及错误更正、暂停、删除机制。

如果来源细节仅因商业秘密不能公开，可向客户合规团队或独立审查方保密展示；不能因此完全免于核验。赔偿条款能分配损失，不能改变取得方式本身的性质。

### 9.2 小样验收

先安排相同规格的 20 次三平台配对任务，覆盖正常、缺货、会员或特别优惠等若干情况，记录首次交付与重采成本。数量用于流程验证，不用于声称达到 99% 准确率。

如继续，按实际风险设计更大盲测集：同时记录配对完成率、关键字段正确率、场景一致率、错误报价导致错误动作的比例、刷新延迟、可用授权比例。人工核验也要留依据，并对部分样本双人复核。

有效报价的定义建议为：门店与商品组合一致、关键场景齐全、有可核对证据、时效合格、用途被允许。单纯返回了一条价格，不计有效交付。合法取得的“缺货/不配送”是单独的有效状态信息，不伪装成有效价格。

## 10. 失效和撤销后，产品怎么处理

| 情况 | 产品行为 |
|---|---|
| 来源权限过期或撤销 | 暂停新处理与受影响输出；标出关联报告；按合同和法律处理删除、保留与通知 |
| 竞对证据过期 | 保留为历史观察；执行前要求刷新，不用旧报价做当前资金建议 |
| 同款映射被否定 | 撤回依赖该映射的候选；保留版本和更正记录 |
| 费用明细缺失 | 仍可展示经核验的应付报价；不强行解释出资或拆出不存在的优惠项 |
| 本平台成本未到齐 | 只展示价格和缺口，不计算确定收益 |
| 研究参与者撤回 | 停止后续处理，按适用依据处理源图与关联数据；必要法定记录隔离保存 |
| 模型抽取失败 | 转人工或标记待核验，不生成猜测值 |
| 无法形成足够实验样本 | 显示结果不确定，继续观察或停止；不把不显著当作无影响 |

前台展示已脱敏数据，后台也必须有最小权限、加密、访问日志和备份删除流程。只把敏感字段在页面上隐藏，不算完成数据最小化。

## 11. 启动时一次收齐的最小材料

由平台预算负责人和数据负责人提供：

1. 一个具体可调整的补贴动作，其出资方、当前规则、预算范围和审批责任人。
2. 一份字段说明及少量合法测试样本：订单/完成、退款、平台出资、收入成本、实验或可比人群口径。无需先导出个人明细。
3. 现有竞对截图或数据源清单，以及其取得与使用依据。资料不完整时明确缺什么，不默认为获准。
4. 10 家门店及 20 个商品组合，或允许分析团队从获准数据中挑选。
5. 客户允许的部署与模型处理方式、数据保留要求，以及是否允许对照实验。

材料齐全后先跑 20 次任务，记录真实成本和缺失比例，再做软件自动化与数据采购决策。这样最早失败的是可以低成本验证的数据假设，而不是已经投入数月后的整套产品。

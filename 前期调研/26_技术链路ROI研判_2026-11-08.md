# 技术链路选择研判：Web、手机模拟器与移动端 App 的 ROI 比较

版本 1.0，2026-11-08。针对「不建议 Web 端，是否可用 web 端手机模拟器，或把工具做成移动端 App，哪条链路 ROI 最高」的研判。结论只到技术选型与投入产出判断；合规边界沿用 [25 号调研](25_采集技术路线颠覆性重构调研_2026-11-08.md) 与合规审计。

## 一页读懂

**推荐主线不变：继续用 Android 设备层（ADB 控制 App），但做两件事——把 UI 读取改成常驻 instrumentation，把设备形态从「专机」换成「普通真机 + 插电常亮」或云手机。** 这是当前唯一能同时覆盖三平台、复用已有 80% 代码、且风控风险最低的链路。

**Web 端手机模拟器不解决问题**：如果指浏览器移动模拟，本质还是 Web，美团 403 与口径差异都还在；如果指 Android 模拟器，本质还是 App，但模拟器是风控识别重点，风险高于真机。

**移动端自研 App 的 ROI 最低**：需要把采集逻辑从 TypeScript 重写为 Android 原生，30–60 人日，且仍然需要一台专用手机，只是省掉电脑与 USB——用 30 人日换「不用连电脑」，不划算。

## 1. 先辨析三个前提

### 1.1 「京东外卖没有 PC 端」

准确说法是：京东外卖没有 PC 客户端，也没有面向 PC 的桌面版网页；但有移动 H5——`hour.jd.com`（京东秒送），本机实测 200、6.6 秒加载、匿名可见商品与价格。公开项目 dsh-meituan 已用它跑到「提交订单页」并读回全部金额。所以「没有 PC 端」成立，「没有网页端」不成立。

### 1.2 「美团被 403」

准确说法是：美团外卖 H5 的**登录态内容接口**对账号返回 403（`X-Forbid-Code`，账号级限制），匿名列表在本机也加载失败（风控与定位）。这不是浏览器问题，换 UA、换无头/有头都失败。结论成立：美团 Web 当前不可用于结算价采集。

### 1.3 「三平台不能在一个电脑/手机上取数，会有风险」

这个担心部分成立，但要拆开看：

- **设备指纹关联**：同一台设备登录多个平台账号，各平台都能记录设备指纹。用「一平台一设备」可以降低关联，这是现有计划已经在做的。
- **IP 关联**：三台手机连同一个办公 WiFi，出口 IP 相同；换成三个浏览器会话跑在一台电脑上，出口 IP 也相同。**换技术栈并没有改变 IP 这一层**。真正隔离需要不同网络出口，但项目禁止代理伪装，所以做不到也不该做。
- **平台间数据不互通**：京东、美团、淘宝闪购是竞争对手，不会共享账号或行为数据；各平台只能基于自己的设备/IP/账号信号判断。所以「同一台电脑取三平台数据」的风险，本质是「三个账号在同一 IP 下被各自平台分别识别」，不是平台之间串数据。

结论：这个担心不能靠换链路解决，只能靠「一平台一设备一账号」的运营约束缓解；而 IP 层风险在任何方案下都存在。

## 2. 候选方案矩阵

| 编号 | 方案 | 改造人日 | 硬件月成本 | 单任务耗时 | 三平台覆盖 | 风控风险 | 口径真实性 |
|---|---|---|---|---|---|---|---|
| A | 真机 + ADB + 常驻 instrumentation | 5–10 | 0（已有设备） | 30–45 秒 | 三平台全覆盖 | 低（真机最像人） | 高（App 是真实入口） |
| B | 云手机 + ADB（阿里云无影等） | 2–3（ADB 兼容，代码几乎不改） | 91–265 元/台 | 30–45 秒 + 云延迟 | 三平台全覆盖 | 中高（机房 IP、虚拟传感器） | 高（仍是 App） |
| C | PC 浏览器 Web（Playwright） | 15–25 | 0 | 15–40 秒（推断） | 仅京东 + 淘宝闪购 | 中高（IP/账号限速） | 中（H5 可能降级） |
| D | 浏览器「手机模拟」（移动 UA / Playwright mobile） | 15–25 | 0 | 同 C | 同 C | 同 C | 同 C |
| E | Android 模拟器（Bluestacks/AVD） | 5–10 | 0 | 30–45 秒 | 三平台全覆盖 | 最高（模拟器是重点识别对象） | 中 |
| F | 自研移动端 App（AccessibilityService 自动操作） | 30–60 | 0 | 20–40 秒（省 ADB 开销） | 三平台全覆盖 | 中 | 高，但仍需专用手机 |

关键判断：

1. **D 不是独立方案**：浏览器移动模拟只是把 Web 页面伪装成手机，美团 403 与 H5 与 App 的口径差异都不变。
2. **E 的风险最高**：行内风控厂商把「虚拟设备识别」当卖点，模拟器跑外卖 App 被识别的概率高于真机；device-accel 调研也不建议作为主通道。
3. **F 的开发成本被低估**：现有采集逻辑（页面理解、字段核对、恢复、证据）都在 TypeScript 里，搬进 Android App 等于重写；AccessibilityService 还要处理各家 App 兼容、无障碍权限、后台保活、Android 版本差异。收益只是「不用连电脑」。
4. **C 的覆盖不完整**：美团这条线缺了，三平台统一就破了；而淘宝闪购 Web 与 App 的优惠/资格差异还需要对照实验。

## 3. ROI 排序与结论

| 排序 | 方案 | 理由 |
|---|---|---|
| 1 | **A 真机 + 常驻读取** | 复用已有代码，5–10 人日换 3–5 倍提速；三平台全覆盖；风控风险最低；数据口径最真实 |
| 2 | **B 云手机 + 常驻读取** | 解决「不想管物理设备」；代码几乎不改；成本 91 元/台/月起；但风控中高，需 1 台试点两周 |
| 3 | C 单平台 Web 补充 | 只在淘宝闪购单平台有价值；破坏统一调度；等 A 做完再评估 |
| 4 | E Android 模拟器 | 免费但风控最高，容易白忙 |
| 5 | F 自研 App | 30–60 人日换「不连电脑」，边际收益太低 |
| 6 | D 浏览器手机模拟 | 相对 C 无新增价值 |

**最终推荐链路：Android 设备层（ADB）+ 常驻 instrumentation 为主；设备形态按你的接受度选普通真机（插电常亮）或云手机；不迁 Web，不做自研 App。**

这条链路能同时满足：

- **提效**：单任务 116.7 秒 → 30–45 秒（常驻读取 10–20 倍提速），热启动 49 秒 → 10–20 秒。
- **去锁屏**：插电 + `svc power stayon true` 保持常亮，屏幕不灭就不进 keyguard，不需要把设备设成「无锁屏」。
- **去专机**（可选）：换云手机后没有物理设备，一台电脑连多台云手机。
- **三平台统一**：这是唯一能同时跑三个 App 的通道。
- **数据真实**：App 是用户真实下单入口，比 H5 更可信。

## 4. 分阶段落地

| 阶段 | 内容 | 人日 | 依赖 |
|---|---|---|---|
| 1 | 真机常驻 instrumentation + 插电常亮配置，京东单店 20 次复测 | 5–10 | 现有测试手机 |
| 2 | 跨机型与多设备并行（M1/M3 计划不变） | 按 24 号计划 | 第二台设备 |
| 3 | 云手机试点（1 台、单平台、两周），验证风控与 ADB 兼容 | 2–3 | 云手机账号与费用 |
| 4 | 美团、淘宝闪购接入（沿用 24 号 M5/M6） | 按 24 号计划 | 页面样本与许可条件 |

Web 路线暂不作为主线；如果阶段 3 云手机风控过高，再回来评估「淘宝闪购单平台 Web」作为降级补充。

## 5. 需要用户确认

1. 接受主线为「Android 设备层 + 常驻读取」，而不是 Web 或自研 App。
2. 设备形态：普通真机（1–2 台，插电常亮，不需要无锁屏设置）还是云手机（91 元/台/月起，先 1 台试点）。
3. 阶段 1 是否立即开工——它不依赖任何新决策，也不改变现有业务逻辑。
4. 若坚持「一个设备也不要」，则只有云手机路线，且需接受风控中高风险。

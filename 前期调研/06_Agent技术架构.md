# 06 Agent 架构：让系统自己找问题、写建议、追结果

> 2026-11-04 归档提示。本篇保留历史研究及其当时的假设。当前范围与开发约束以 [项目规范](../agent.md)、[数据治理表](../数据治理/数据治理表.md) 和 [当前采集路线](11_零外部资源下的数据采集路线_2026-11-04.md) 为准。

## 结论

用“专家 Agent 加确定性内核”的架构。采集、解析、匹配、计价、分析、策略、行动、审计各司其职。LLM 负责判断、解释和生成，代码负责计算、调度和执行。第一版不要做万能 Agent，也不要做多 Agent 编排，先把脚本和规则跑通，再把需要判断的环节交给 Agent。

## 1. 设计原则

1. 确定性内核，Agent 做边缘。价格计算、门槛判断、状态流转用代码；语义匹配、异常解释、策略生成用模型。
2. 证据优先。每条结论都要能回溯到截图、观测记录、探针编号和时间戳。
3. 人在回路。面向商家的动作必须由人确认，系统只给建议和证据。
4. 成本分层。简单样本用便宜模型，难样本用贵模型，浏览器 Agent 只做兜底。
5. 可观测。每次 Agent 调用有输入、输出、耗时、成本、置信度，能回放。
6. 可替换。模型、OCR、采集器都是可插拔组件，不绑定单一供应商。

## 2. Agent 角色

| Agent | 职责 | 输入 | 输出 | 工具 | 模型档位 |
|---|---|---|---|---|---|
| 调度 Agent | 决定今天采什么、算什么、发给谁 | 日历、告警、数据新鲜度 | 任务清单 | 工作流引擎、队列 | 规则加轻量模型 |
| 采集 Agent | 选择脚本或浏览器 Agent，处理页面改版 | 门店和 SKU 清单 | 原始页面、截图 | Playwright、Appium、Stagehand | 脚本优先，Agent 兜底 |
| 解析 Agent | 从页面和截图抽取商品、价格、优惠、费用 | 原始页面、截图 | 结构化字段 | OCR、VLM、规则 | 轻量 VLM |
| 对齐 Agent | 匹配 POI 和 SKU，给出置信度 | 结构化字段、图谱 | 统一 ID、置信度 | 向量检索、交叉编码器、VLM | 小模型加 VLM |
| 计价服务 | 算到手价、拆价差 | 统一 ID、优惠规则 | 价格分布、分解结果 | 规则引擎 | 无模型 |
| 分析 Agent | 找异动、做归因、写洞察 | 价格分布、订单、活动 | 异动清单、归因 | SQL、统计、图谱 | 主力 LLM |
| 策略 Agent | 生成动作建议、排序、写话术 | 归因、案例库、约束 | 动作队列 | 检索、规则、模拟 | 主力 LLM |
| 行动 Agent | 派单、催办、收结果、更新状态 | 动作队列、工单 API | 状态变更 | 企微、飞书、内部工单 | 轻量模型 |
| 补贴 Agent | 算必要补贴线，找超补，提调拨建议 | 价格、补贴成本、订单 | 超补清单、调拨建议 | 规则、弹性模型 | 主力 LLM 加规则 |
| 审计 Agent | 查数据质量、合规、模型漂移 | 日志、样本、规则 | 审计报告、告警 | SQL、规则 | 轻量模型 |

### 2.1 调度 Agent

调度 Agent 是入口。它每天早上检查三件事：数据是否齐全、昨天有没有未处理的告警、今天有没有 campaign。然后生成任务清单，分给采集、解析、分析。

调度用规则加轻量模型，不用主力 LLM。规则负责时间、优先级、依赖；模型只处理“今天该重点关注哪些店”这类模糊判断。

### 2.2 采集 Agent

采集 Agent 的核心是选择采集方式。稳定的页面用脚本，改版频繁或 DOM 复杂的页面用浏览器 Agent，需要登录态或真实券的页面交给真人面板。

采集 Agent 要能处理三类异常：选择器失效、验证码、页面结构变化。选择器失效时，先尝试备用选择器，再切浏览器 Agent，最后转人工。验证码出现时，停止该账号，降频，记录原因。页面结构变化时，触发解析 Agent 重新学习字段。

### 2.3 解析 Agent

解析 Agent 把页面和截图变成结构化字段。优先用 OCR 加规则，价格、费用、优惠这些字段位置相对固定；OCR 置信度低时，切 VLM 做整页理解。

解析结果要带三个置信度：字段级、页面级、跨源一致性。字段级看 OCR 置信度，页面级看整页结构是否完整，跨源一致性看同一门店同一 SKU 在不同来源的价格是否接近。

### 2.4 对齐 Agent

对齐 Agent 做两件事：POI 匹配和 SKU 匹配。先用规则和向量召回候选，再用交叉编码器打分，低置信度交 VLM 或人工。

对齐 Agent 的输出要包含“不可比”这个选项。两个商品规格不同、套餐内容不同、份量不明，都应该判不可比。强行匹配比不匹配更危险，因为错误会一路传到策略层。

### 2.5 计价服务

计价服务用确定性代码实现。它加载优惠规则，按固定顺序计算，输出价格分布和价差分解。LLM 可以解释结果，不能参与计算。

计价服务要有版本号。优惠规则变了，历史价格要能用旧版本复算。否则今天的日报和上周的日报对不上，运营会失去信任。

### 2.6 分析 Agent

分析 Agent 负责三件事：异动检测、价差归因、洞察生成。

异动检测用统计方法，CUSUM、EWMA、孤立森林都可以。价差归因用加法分解，把总价差拆到菜单、活动、券、履约。洞察生成用 LLM，把数字翻译成运营能读懂的话，比如“这家店的价差主要来自配送费，菜价与竞对接近”。

分析 Agent 的每条结论都要带证据。没有证据的结论不进日报。

### 2.7 策略 Agent

策略 Agent 根据归因、案例库和业务约束生成动作建议。它的输入包括：价差结构、商户配合度、历史动作效果、补贴预算、合规约束。

策略 Agent 输出结构化动作，方便系统执行和统计：

```json
{
  "store_id": "S001",
  "sku_id": "SKU001",
  "gap": -3.0,
  "main_cause": "over_subsidy",
  "action": "平台补贴从3元降到1元，仍比竞对低1元",
  "action_type": "reduce_subsidy",
  "subsidy_cost": 3.0,
  "necessary_subsidy": 1.0,
  "over_subsidy": 2.0,
  "owner": "补贴运营-国贸",
  "expected_effect": "单均节省2元，预计订单不下滑",
  "confidence": 0.72,
  "evidence": ["obs_001", "obs_002", "case_017"]
}
```

跟价场景把 `action_type` 换成 `close_gap`，`over_subsidy` 为 0。策略 Agent 要先检索案例库，找相似场景下哪些动作有效。没有案例时，用规则剧本兜底。动作建议要能解释，不能只给结论。

### 2.8 行动 Agent

行动 Agent 把动作送进城市运营的现有工具，企微、飞书或内部工单。它负责派单、催办、收结果、更新状态。

行动 Agent 的权限止于生成调价建议、活动报名链接和沟通话术，调价与活动报名由商家确认后执行。补贴调拨是内部动作，可以由平台自己执行；降补涉及的商家补贴要提前告知，不能暗中扣减。2026 年的价格新规禁止平台强制商家降价和自动跟价，这条边界要写进 Agent 的工具权限。

### 2.9 补贴 Agent

补贴 Agent 负责算“补多少才够”。它拿三个数：竞对到手价、京东到手价、京东补贴成本。补贴成本按出资方拆开，平台补贴和商家折扣分开算。先算目标价和必要补贴，再算超补金额。

补贴 Agent 输出调拨建议，比如“这家店每月可省 3 万，转到隔壁打不过的 5 家店”。降补建议要经过增量实验验证，确认订单不掉再执行。

### 2.10 审计 Agent

审计 Agent 每周跑一次，检查四件事：

1. 第一项查数据质量，包括覆盖率、准确率、新鲜度和重复率。
2. 第二项查合规，包括采集日志、授权记录、敏感字段和对外输出。
3. 第三项查模型，看匹配准确率是否漂移、解析置信度是否下降、策略建议的采纳率是否变化。
4. 第四项查成本，统计每个 Agent 的调用次数、token 消耗和单条观测成本。

审计结果进周报。发现异常时，自动降级或停用相关 Agent。

## 3. 数据与工具栈

| 层 | 推荐 | 备选 | 说明 |
|---|---|---|---|
| 原始存储 | 对象存储 | 本地文件 | 截图、页面、日志 |
| 结构化存储 | PostgreSQL | MySQL | 门店、SKU、规则、动作、补贴成本 |
| 分析存储 | ClickHouse | DuckDB | 价格时序、聚合分析 |
| 向量检索 | pgvector | Milvus | SKU 和门店召回 |
| 工作流 | Airflow | Temporal | 批处理用 Airflow，长事务用 Temporal |
| 转换 | dbt | 手写 SQL | 指标口径统一 |
| 解析 | PaddleOCR 加 VLM | 云 OCR | 中文菜单和截图 |
| 匹配 | 交叉编码器 | LLM 直接判断 | 成本和稳定性更好 |
| 浏览器 | Playwright | Stagehand、browser-use | 脚本优先，Agent 兜底 |
| App 自动化 | Appium、UIAutomator | 云手机 | 外卖 App 采集 |
| API | FastAPI | Flask | 内部服务 |
| 前端 | 飞书卡片、Metabase | 自建后台 | 先用现成工具 |
| 告警 | 飞书机器人、企微 | 邮件 | 和现有工作流一致 |

## 4. 编排

### 4.1 日流程

```text
06:00  广扫采集，覆盖 50 家店的全菜单
07:00  解析截图和页面，抽字段
08:00  POI 和 SKU 对齐，低置信度进人工队列
09:00  计价，算到手价和价差
10:00  分析，找异动，做归因
11:00  生成日报和动作建议
14:00  城市运营处理工单
18:00  晚市哨兵采集
21:30  夜宵哨兵采集
23:00  汇总当日执行情况和数据质量
```

编排工具用 Airflow 跑批处理，动作状态用 Temporal 或数据库状态机。到 V2 需要多 Agent 协作时，再引入 LangGraph 一类框架，底层仍然调用同一批工具和数据。

### 4.2 事件触发

除了定时任务，还要支持事件触发：

- 哨兵店价格变化超过阈值，立即重算并告警。
- 竞对 campaign 开始，提前提高采样频次。
- 新店开业或 POI 变更，触发匹配和基线采集。
- 城市运营反馈“这家店不对”，触发人工复核。

### 4.3 状态机

动作状态用状态机管理，不用自由文本：

```text
待确认 → 已派单 → 处理中 → 已调价/已加活动 → 观察中 → 收敛/未收敛
```

每次状态变更记录操作人、时间、证据、备注。状态机的好处是可统计、可追责、可复盘。

### 4.4 人在回路

三个节点必须人工确认：

1. 低置信度匹配，人工确认 POI 和 SKU。
2. 面向商家的动作，城市运营确认后再发。
3. 补贴和价格调整，商家确认后执行。

人工确认是风险控制，代价是少量效率。系统可以自动生成 80% 的建议，最后 20% 的判断留给人。

## 5. 模型与成本

| 任务 | 模型档位 | 月调用量估算 | 月成本估算 |
|---|---|---|---|
| 截图 OCR 和字段抽取 | 轻量 VLM 或 OCR | 2 万张 | 500 到 2000 元 |
| SKU 候选打分 | 交叉编码器 | 10 万对 | 300 到 1000 元 |
| 异动解释和日报生成 | 主力 LLM | 1000 次 | 500 到 2000 元 |
| 策略建议 | 主力 LLM | 200 次 | 500 到 2000 元 |
| 浏览器 Agent 兜底 | 多模态 Agent | 100 到 500 次 | 500 到 3000 元 |
| 合计 |  |  | 2300 到 1 万元 |

这是试点规模的成本估算，实际取决于模型单价、截图复杂度和调用次数。规模化后，解析和匹配的成本会随量上升，分析和策略的成本增长较慢。

成本控制的三个手段：

1. 缓存。同一门店同一 SKU 的解析结果缓存，页面没变不重复调用。
2. 级联。简单样本走规则和小模型，只有歧义样本走大模型。
3. 批处理。非实时任务合并成批，减少冷启动和重复上下文。

## 6. 评估

### 6.1 黄金集

上线前建三个黄金集：

- POI 对准备 500 对，覆盖连锁、单体、同品牌多店和地址变更。
- SKU 对准备 1000 对，覆盖标准品、套餐、加料、规格差异和图片相似。
- 标准篮准备 200 个，覆盖 5 个品类、3 个商圈和 4 类账号。

黄金集由人工标注，作为回归测试的基线。每次改匹配规则或换模型，都跑一遍。

### 6.2 离线指标

| 指标 | 目标 |
|---|---|
| POI 匹配准确率 | 95% |
| POI 匹配召回率 | 90% |
| SKU 匹配准确率 | 90% |
| SKU 自动匹配覆盖率 | 70% |
| 到手价误差 | 3% 以内 |
| 解析字段完整率 | 95% |

### 6.3 在线指标

| 指标 | 目标 |
|---|---|
| 数据新鲜度 | 哨兵 30 分钟内 |
| 日报准时率 | 95% |
| 建议可执行率 | 60% |
| 派单执行率 | 30% |
| 价差收敛率 | 20% |
| 超补识别准确率 | 80% |
| 补贴节省金额 | 试点期达到预算的 10% |
| 单店日成本 | 200 元以内 |

### 6.4 Agent 评估

Agent 的评估和传统模型不同，重点看三件事：

1. 证据覆盖：每条结论是否有可追溯的证据。
2. 幻觉率：建议中引用的数据、门店、商品是否真实存在。
3. 建议质量：城市运营对建议的采纳率和评分。

每周抽 20 条建议做人工评分，记录“可执行、部分可执行、不可执行”。评分结果回流到策略 Agent 的提示词和案例库。

## 7. 安全与治理

### 7.1 权限

- 权限按角色划分，总部看全量，城市看辖区，BD 看自己商户，商家只看自己。
- 敏感字段在前端脱敏，手机号、地址和订单号默认隐藏。
- 所有导出都记录日志，能查到谁在什么时间导出了什么数据。

### 7.2 数据安全

- 原始截图加密存储，访问留痕。
- 个人信息最小化，不采集用户姓名、手机号、身份证。
- 数据保留期限明确，过期删除。
- 供应商数据合同写明用途、期限、删除义务。

### 7.3 Agent 安全

浏览器 Agent 会读取外部页面，存在提示注入风险。防护措施：

- 把网页内容当不可信输入，不执行页面里的指令。
- 限制可访问域名，只允许目标平台和公开数据源。
- 工具调用白名单，Agent 不能调用未授权的接口。
- 沙箱运行，隔离网络和文件系统。
- 关键动作人工确认。

### 7.4 合规

- 采集日志保存至少 6 个月。
- 每次对外输出带数据来源和免责声明。
- 不做自动跟价、自动改价、强制商家参加补贴。
- 定期做合规审计，发现问题立即停用相关功能。

## 8. 从 MVP 到规模化

### MVP，第 1 到 2 周

- 脚本采集加人工上传截图。
- OCR 加规则解析。
- 人工确认 POI 和 SKU。
- 规则引擎算到手价。
- Markdown 或飞书日报。

这个阶段不用 Agent，验证数据口径和业务价值。

### V1，第 3 到 4 周

- 加 LLM 匹配和解析兜底。
- 加分析 Agent，自动找异动、写归因。
- 加飞书机器人，城市运营可以直接反馈。
- 加数据质量看板。

### V2，第 5 到 8 周

- 加策略 Agent，生成动作建议。
- 加补贴 Agent，算必要补贴线，出超补清单。
- 加行动 Agent，接工单，跟踪执行。
- 加案例库，记录动作和结果。
- 加 A/B 分析，评估动作效果。

### V3，第 9 周以后

- 加预测信号，竞对 campaign 预警、新店预警。
- 加仿真，模拟不同补贴和定价方案的后果。
- 加多城市扩展，按城市配置规则和模型。

## 9. 不做什么

1. 不做通用爬虫农场。采集是成本中心，护城河在数据归一和行动闭环。
2. 不让 LLM 算钱。金额计算交给规则引擎。
3. 不做自动改价。合规和信任都不允许。
4. 不做纯聊天界面。运营需要清单和工单，聊天只能做入口。
5. 不在第一版做多 Agent 编排。先把单点能力跑通，再考虑协作。
6. 不追求 100% 自动化。最后 10% 的人工判断是质量保证。
7. 不做无成本约束的全面跟价。补贴预算有限，跟价要有选择。

## 10. 技术选型建议

批处理用 Airflow，动作状态用 Temporal 或数据库状态机；结构化数据放 PostgreSQL，时序放 ClickHouse；匹配用 pgvector 加交叉编码器；解析用 PaddleOCR 加 VLM 兜底；采集用 Playwright 和 Appium，浏览器 Agent 只做异常兜底；分析和策略用主力 LLM，计价和状态流转用代码。整套系统保持模型无关，方便按合规和成本切换供应商。

# 三平台并行采集长程开发计划与规约

版本 1.0，2026-11-08。依据用户本轮目标与三份只读审计（跨机型、设备并发与锁屏、时延预算）编写。本文档定义最终交付目标、里程碑、验收口径和工程规约；实施过程中按已确认结论更新，不把规划写成已完成能力。

## 一页读懂

**最终交付**：BD 输入城市、区县、品牌、完整分店名、商品与规格，系统并行在京东、美团、淘宝闪购各采一次指定单品报价，交付现价、结算应付、费用明细、证据和失败原因；不受单店单机限制，不受锁屏影响；正确性 98% 以上；从提交到结果可读约 120 秒。

**当前差距**：京东单店单机质量已验证（20 次连续 20/20），但跨机型未验证、三平台只有京东、采集是单设备单进程、锁屏即停止、正确性样本只有 20 次、京东冷启动结束 P50 已 124.3 秒。

**关键判断**：三平台并行只缩短总墙钟，不改善单平台链路；120 秒目标的前提是京东冷启动先压到 90 秒级，并把设备与模型预热常驻。正确性 98% 不能用 20 次通过来声称，需要按置信区间设计样本量。

**执行顺序**：①跨机型通用化 → ②京东首页出发提速 → ③并行通道化与值守 → ④美团接入 → ⑤淘宝闪购接入 → ⑥三平台端到端验收 → ⑦固化交付。每个里程碑有独立验收，不通过不进入下一项。

**需要先决策**：设备数量与是否接受专用机无锁屏、120 秒的计时口径、三平台账号与点位、淘宝闪购许可推进方式、正确性验收的样本量与人工复核投入。

## 1. 目标与可验收定义

### 1.1 产品目标

一次任务 = 一个「城市 + 区县 + 品牌 + 完整分店名 + 商品 + 规格 + 数量」的比价请求。系统据此生成一个比较组，包含京东、美团、淘宝闪购各一条采集任务，绑定各自通道并行执行，交付：

| 交付项 | 要求 |
|---|---|
| 门店匹配 | 完整分店名、城市、区县、营业地址可核对；错店必须停止而不是换店 |
| 商品匹配 | 单品名称、规格、选项、数量可核对；套餐、规格不明、找不到必须停止 |
| 价格字段 | 现价、结算应付、商品小计、包装费、配送费、其他费用、优惠、可售状态；未知留空并给原因 |
| 证据 | 门店、规格、现价、结算、恢复的证据截图与时间，脱敏后保存 |
| 失败语义 | 售罄／休息／不配送／未达起送为业务无报价；访问受限、锁屏、掉线为技术失败，分别记录 |
| 组状态 | 三平台各自完成，组级给出 delivered（全部终止）与 partial（部分失败） |

### 1.2 指标定义

| 指标 | 定义 | 目标 |
|---|---|---|
| 正确性（任务级） | 单平台一次采集的门店、规格、全部金额字段与独立真值一致，且证据完整，记为正确 | ≥98%（点估计），95% 置信下界 ≥97% |
| 正确性（字段级） | 已交付金额字段中与真值一致的占比 | ≥99.5% |
| 组级全对率 | 三平台均正确的组数 ÷ 完成组数 | ≥96%（单平台 98% 时三平台串联约 94%，单独统计，不并入 98% 定义） |
| 交付时延 | 提交时刻到结果与证据可读时刻 | P50 ≤120 秒，P90 ≤180 秒 |
| 通用性 | 通过验收的机型数量与分辨率档位 | ≥2 个机型、≥2 个分辨率档位、≥2 个 Android 版本 |
| 可用性 | 无人值守连续运行中计划任务完成率 | ≥95%，锁屏/掉线/授权到期有告警 |
| 覆盖率 | 三平台均有真实报价的组占比 | 接入全部门店后 ≥95% |

正确性目标按用户「98% 以上」解释为单平台任务级 98%、字段级 99.5%；组级全对率单独报告，避免把三平台串联误差混入同一数字。

### 1.3 计时口径

- **T0**：服务端收到提交请求并落库的时刻。
- **T1**：组内三条任务全部终止（success／unavailable／blocked／failed）的时刻。
- **T2**：最后一条证据落库、结果接口可读的时刻。交付时延 = T2 − T0。
- 设备领取等待单独记录为 `queueMs`，不计入交付时延但必须在报告中单列；设备全忙时的排队是容量问题，不是采集速度问题。
- 冷启动：目标设备当前不在目标门店页或目标 App 未激活。热启动：设备已在目标门店页且近期身份证据可复用。两种场景分别统计，不混算。
- 阶段耗时含并行操作，不能简单相加；报告同时给关键路径和阶段分布（现有 `elapsedMs`、`quoteMs`、`queueMs`、`timings` 口径沿用）。
- 新增计时点：提交落库时刻、设备预热命中、每次 UI 树读取耗时（页面、节点数、dump/拉取/解析分段）、每次输入前的前台检查、模型服务端排队与推理、证据索引完成时刻、前端可见延迟、三平台各自的平台交付时刻。交付时延终点取「报价可读、证据可查、写库完成」三者中最晚者；恢复与预热单列，不并入报价时延。

### 1.4 验收分层

| 层级 | 范围 | 通过线 |
|---|---|---|
| L0 单元与回放 | 每次提交 | 类型检查、单元测试、页面回放通过 |
| L1 单机单店 | 20 次连续 | 质量 20/20，恢复 20/20，性能 P90 达标 |
| L2 跨机型 | 2 机型各 10 次，同店同品同时段 | 功能 10/10，金额一致或差异可解释，几何门禁全过 |
| L3 多设备并行 | 2 台并行 20 组 | 组交付 20/20，无设备/账号串扰，租约无泄漏 |
| L4 三平台 | 三平台各 50 组（≥2 店） | 单平台正确率 ≥98%，组 partial 时语义正确 |
| L5 无人值守 | 连续 8 小时、24 小时 | 计划完成率 ≥95%，异常有告警，恢复后可继续 |

任何层级未通过不得发布「已适配」「已稳定」「已接入」的结论；单机、单店、单平台的通过结果不得外推到其他层级。

## 2. 现状与差距

### 2.1 已具备的能力

| 能力 | 状态与证据 |
|---|---|
| 京东单店单品采集 | 20 次连续 20/20 完整成功，金额 20 次一致，全部自动恢复（19、23 号文档） |
| 坐标归一化 | 点击用控件 bounds 中心，滑动用容器 bounds 比例，证据裁剪按截图/视口比例缩放；无物理像素硬编码（跨机型审计结论 1） |
| 模型坐标换算 | 视觉模型返回输入图绝对像素，两处调用均按输入图尺寸换算或同图比较（跨机型审计结论 3） |
| 跨平台调度雏形 | `Scheduler` 已有按平台 worker 与并行循环，任务契约已含三平台枚举 |
| 证据与失败体系 | 证据截图、SHA-256、逐字段核对、失败分类、执行日志、步骤级耗时 |
| 恢复与中断 | 服务重启把运行中任务标记中断、暂停真机账号与设备、清空锁 |

### 2.2 差距

| 差距 | 现状 | 影响 |
|---|---|---|
| 跨机型 | 只在一台设备校准；无设备型号/分辨率/density/方向/字体缩放采集与门禁；无 overlay 缩放系数与 safe area 校验；证据无几何元数据 | 「换机型可用」目前无法证明，只能靠重新校准 |
| 单机校准的固定比例 | 京东搜索页 17%–72% 屏高裁剪 + 缩放到 640 宽 + 模型点击；商家标签与结果头部比例窗口；结算隐私遮罩 24% 屏高、兜底滑动固定 0.78 宽 | 换宽高比、大字体、折叠/平板时整条流程可能被挡在 blocked |
| 单设备单进程 | 每平台只允许一条来源；调度 worker 键为「模式:平台」，同平台永远单并发；进程锁 + 单 SQLite；设备锁无 TTL | 无法登记第二台设备，无法并行，崩溃后设备可能长期占用 |
| 锁屏 | 只唤醒不解锁；锁屏即 blocked；不重试、不暂停设备、不告警、无换设备 | 夜间锁屏会让整批任务静默失败 |
| 三平台 | 只有京东有真实适配器与来源配置；美团、淘宝闪购无页面样本与控件；淘宝闪购许可前置未满足 | 无法并行采数 |
| 正确性样本 | 20 次单店单品通过，样本量不足以支撑 98% 结论（20 次 0 错误时 95% 下界约 86%） | 不能对客户宣称 98% |
| 时延 | 京东冷启动结束 P50 124.3 秒、报价 P50 116.7 秒 | 已超 120 秒交付目标；并行不改善单平台耗时 |
| 内部数据 | 京东订单、合同、财务未接入，UE 工作台仍为示例数据 | 比价可交付，经营结论不可交付 |

### 2.3 三个关键判断

1. **并行不等于提速。** 三平台并行后的墙钟约等于最慢平台加调度开销。京东冷启动单平台已 124 秒，不做单平台提速就无法达到 120 秒。
2. **热启动路径已经达标。** 门店内继续场景结束 P50 58.5 秒、P90 59.2 秒。说明页面操作本身不慢，慢在冷启动的进入应用、搜索门店、找商品；逐任务复算显示 UI 树读取占总耗时约 79.5%（每轮约 26 次、每次约 3.63 秒），模型调用仅约 6.6%。因此提速主线是减少 UI 树读取次数与等待，不是减少模型调用。
3. **98% 需要设计样本。** 20 次全对只能说明下界约 86%；150 次全对的 95% 单侧下界约 98.0%。最终验收建议累计 500 次、错误不超过 10 次。

## 3. 里程碑计划

顺序按用户要求：先跨机型，再提速，再做并行与值守，最后接竞对并固化。每个里程碑结束时产出一份验收记录，更新对应文档与基线。

### M1 跨机型通用化（预计 7–9 人日）

目标：同一套代码在两种分辨率、两种 Android 版本的设备上完成同一门店单品采集，且能证明不依赖绝对坐标。

主要工作：
1. 设备几何档案与门禁：采集 `ro.product.model`、`ro.build.version.sdk`、`wm size`、`wm density`、方向、`font_scale`，写入任务与证据；超出支持矩阵返回 `unsupported_device_geometry` 并阻断。
2. 京东搜索页去固定裁剪：用结果容器/卡片的实际 bounds 计算裁剪区域，删除固定 17%/55% 与固定 640 缩放；统一「图片点 → 逻辑坐标」换算函数。**已接入采集流程：容器可用时按实际 bounds 裁剪，容器不可用时回退固定比例；7 项单测覆盖，待大促后真机验证。**
3. 比例窗口改控件相对布局：商家标签、结果头部改为相对同级控件或容器定位；比例阈值移入来源配置并标注校准设备。**已接入：`pilotStoreHeader` 统一委托参数化窗口函数，默认窗口与历史行为一致，换机型只改配置；待真机验证。**
4. 证据隐私改节点驱动：结算顶部遮罩用地址/点位节点 bounds 并集，比例仅作兜底并记录兜底原因；搜索页证据按卡片 bounds 裁剪。**已接入：优先按配送点位锚点计算遮罩带，找不到锚点时回退固定比例；4 项单测覆盖，待真机验证。**
5. overlay 缩放系数与 safe area 校验；方向变化、`wm size/density` 变化立即中止。
6. 参数化单测矩阵（多种逻辑尺寸 × 截图尺寸）、点击坐标单测、静态门禁（禁止裸物理像素常量）。

验收（L2）：2 台不同分辨率/Android 版本各 10 次，功能 10/10、金额一致或差异可解释、证据尺寸等于 `wm size`、隐私遮罩覆盖地址；动态分辨率矩阵（改 size/density/font_scale）成功率不低于基线 80%；采集中改分辨率必须 fail-safe。

依赖：第二台测试设备与独立通道配置。风险：OEM ROM 的锁屏判定与浮层差异；大字体会改变布局比例。

### M2 京东首页出发提速（预计 3–5 人日）

目标：首页出发报价 P50 ≤90 秒、P90 ≤100 秒；结束 P50 ≤120 秒、P90 ≤130 秒（20 次批次）。

拆解（基于 20 次批次逐任务复算）：

- 冷启动关键路径 P50 124.3 秒 ≈ 首屏树读取（未单列）10.1 + 进入外卖 14.9 + 搜品牌 8.5 + 选候选门店 10.1 + 核对分店 9.8 + 找商品 13.2 + 现价 3.9 + 加购 15.8 + 结算 19.2 + 模型核对 4.8 + 恢复剩余 7.6。分段和 118.3 与实际 124.3 不等，阶段不能相加。
- 根因是 UI 树读取约占总耗时 79.5%（每轮约 26 次、每次约 3.63 秒），模型调用仅约 6.6%。因此提速主线是减少 UI 树读取次数与等待。
- 可优化项按收益排序（推断项已标注）：常驻预置京东外卖首页约 −20.8 秒（推断）；预置或直达目标门店页约 −28.4 秒（推断，能力尚未验证）；菜单预读把找商品 13.2 秒降到 3.4 秒（−9.8，店内继续路径实测对比）；把购物车恢复移出交付口径 −7.6 至 −7.8 秒（口径调整，非提速）；用锚点选店替代模型兜底 −2.3 秒（实测 10/10 走兜底）。

举措：
1. 应用常驻与入口直达：设备保持京东外卖前台或后台，减少冷启动与首屏树读取；模型服务常驻预热。
2. 门店级预置与直达：提交后若设备已在同店，直接进店；否则先做一次短预热（进入外卖首页并加载），再走搜索。若「提交前预置门店页」不可行，保底方案是首页常驻加门店映射缓存，目标 P50 ≤110 秒并如实报告未达 90 秒。
3. 门店映射缓存：品牌 + 完整分店名 + 地址摘要 → 候选卡片特征，命中时跳过视觉模型定位，直接按控件文字点击；只有歧义或未命中才调用模型。
4. 菜单预读与商品直达：复用菜单分类与商品位置，减少滚动轮次与重复 UI 树读取；合并连续读取，按页面状态指纹判断是否需要重读。
5. 质量门槛不变：缓存只复用定位关系，价格、规格与证据每次重读。

验收（L1）：20 次连续，质量 20/20，自动恢复 20/20，性能指标 P90 达标；与提速前同批次对比报告并列。若 20 次未达标，保留失败记录，不把单次最好成绩当结论。

### M3 通道化与并行调度（预计 5–8 人日）

目标：同一平台可以登记多条通道（不同设备/账号/点位），不同通道并行，同一账号串行；一次提交生成三平台同组任务。

主要工作：来源增加通道 id 并允许同平台多条；调度 worker 键改为通道；任务增加 `channel_ref`、优先级、组截止；采集器按通道装配；设备租约 TTL/心跳/代号；设备健康状态与恢复接口；组级交付状态与聚合。**已抽出 `src/domain/channel.ts`：通道类型、集合校验（同平台多通道、设备不可共用）、租约 TTL/心跳/代号/回收、按优先级选择通道，6 项单测覆盖；尚未接入调度器。**

验收（L3）：2 台设备并行 20 组，组交付 20/20，无设备或账号串扰，租约无泄漏，服务重启后能恢复。

### M4 锁屏值守与设备健康（预计 3–5 人日）

目标：专用设备在无锁屏配置下连续 8 小时无人值守，计划完成率 ≥95%，异常有告警。

主要工作：设备配置清单与任务前自检；失败分类（设备类重试一次 → 暂停通道 → 换备用设备 → 告警；账号类暂停并人工处理；业务类不重试）；值守守护进程（服务存活、设备在线、锁屏告警、磁盘与授权检查）；告警通道；人工恢复接口。

验收（L5）：8 小时与 24 小时空跑；强制锁屏、掉线、撤销授权、服务崩溃、授权到期五类故障注入；确认代码没有任何自动解锁或绕过验证码逻辑。

### M5 美团接入（预计 8–12 人日）

目标：美团单店单品真实报价可交付，质量与京东同口径。

工作：来源条件与入口登记；页面样本（门店、菜单、规格、购物车、结算、费用、恢复）；控件与字段绑定；适配器实现（不复用京东控件假设）；单店 5 次 → 20 次 → 双机型 → 并行验收。

验收：L1、L2 在美团成立；跨平台比较要求同店同品、同点位、时差 ≤5 分钟。

### M6 淘宝闪购接入（预计 6–10 人日）

前置：来源许可与访问条件满足，未满足时只做离线样本适配，不登记为已接通。

工作同 M5；另需单独记录许可依据与使用范围。

### M7 三平台端到端验收（预计 5–8 人日）

目标：三平台并行组交付达到 120 秒与 98% 指标。

工作：端到端计时点、组级交付与 partial 语义、容量与排队策略、模型并发治理、错误预算；三平台各 50 组验收（≥2 店）；累计 500 次正确性样本与人工复核。

验收（L4 + 指标）：交付时延 P50 ≤120 秒、P90 ≤180 秒；单平台正确率 ≥98%（95% 下界 ≥97%）、字段级 ≥99.5%；组级全对率 ≥96%；失败与未执行全部计入报告。

### M8 固化与交付（预计 2–3 人日）

工作：冻结技术路径基线（应用版本、代码哈希、页面地图版本、设备与 App 版本、模型版本、支持矩阵）；编写 BD 操作说明与值守手册；整理验收报告索引；把「未验证」与「已验证」分清单列。

## 4. 工程规约

### 4.1 屏幕与机型通用性规约

1. 禁止把物理像素写死为坐标、尺寸或裁剪框。坐标只能来自：控件 bounds、截图与视口的比例、来源配置中的 `layoutProfile`。
2. 每次采集记录设备几何：型号、Android 版本、`wm size`、`wm density`、方向、字体缩放、截图尺寸、视口尺寸、overlay 缩放系数。缺任何一项不得标记为已验证。
3. 几何超出支持矩阵（竖屏手机、逻辑宽 340–480dp、宽高比 1.9–2.4、font_scale 0.85–1.15、中文系统）时阻断并记录 `unsupported_device_geometry`，不猜、不降级硬跑。
4. 布局比例常量必须进来源配置，并注明校准设备与日期；换机型或改大字体必须重新校准并记录。
5. 任何与坐标相关的代码改动，提交时必须附：参数化单测、静态门禁结果、至少一次真机或回放证据。
6. 未在任何第二台设备验证前，文档只能写「单机已验证」，不得写「已适配」。

### 4.2 验收规约

1. 按 L0–L5 分层验收，逐层通过；每层结论只在其范围内有效。
2. 样本量：质量结论至少 20 次连续；正确性结论按统计口径给出样本量、错误数与置信区间，0 错误 150 次可写「95% 下界约 98%」。
3. 失败、未执行、被中断的任务全部计入分母；不得用成功重跑覆盖失败记录。
4. 单店、单机、单平台、单批次的结果必须写明范围，不得外推。
5. 验收报告必须列出「本次未验证项」。

### 4.3 正确性规约

1. 独立真值：每份交付报价由人工对照脱敏证据逐项核对门店、规格、现价、应付与费用；不能用模型的第二次回答充当真值。
2. 统计口径：任务级正确率与字段级正确率分开；组级全对率单独报告。
3. 错误处置：发现错价，该条退出统计并保留原始记录；同一字段连续两次错价必须回退适配器版本并重新校准。
4. 抽样：每平台每店每批至少 100% 全量核对进入验收；日常运行按 10% 抽检并记录抽检结果。
5. 任何「正确」结论必须能定位到证据编号、核对人、核对时间。

### 4.4 时延规约

1. 计时按 1.3 的口径执行，排队时间单列。
2. 性能结论用 P50 与 P90，样本不少于 20 次；只报平均值无效。
3. 冷启动与热启动分别统计；不允许用热启动成绩代表冷启动。
4. 单平台 partial 或 blocked 不得阻塞组交付；组内超时必须按时交付其余结果并标记 partial。
5. 性能目标未达成时保留失败记录，写明瓶颈阶段与证据，不用「接近目标」表述。

### 4.5 设备与值守规约

1. 使用专用测试设备：屏幕锁定设为无、充电时保持唤醒、自动锁屏时间拉长、关闭省电与应用自动更新、固定竖屏、常连电源与网络、仅登录登记的测试账号。
2. 任务前自检：ADB 与序列号、状态、App 版本、亮屏与锁屏状态、电量与充电、网络、模型可达、来源授权剩余时间、通道是否暂停。任一项失败按分类处理。
3. 失败策略：设备类错误在任务预算内重试一次（唤醒、重启应用、重连 adb），仍失败则暂停该通道并可换备用通道；账号类错误暂停账号并告警人工处理；业务无报价不重试。
4. 禁止：绕过密码/PIN/图案/指纹锁屏、自动输入密码、自动确认 USB 调试授权、绕过平台验证码或风控、换号换代理伪装身份。锁屏的唯一出路是告警后人工处理。
5. 租约：设备锁必须带 TTL、心跳与代号；动作前核对代号；只回收「已过期且确认旧 worker 死亡」的租约，禁止双点同一台手机。
6. 值守：服务托管、周期自检、异常告警（锁屏、掉线、授权到期、连续设备类失败）、人工恢复记录操作人与原因。
7. 无人值守验收必须包含故障注入：强制锁屏、拔线、撤销授权、杀服务、授权到期。

### 4.6 三平台并行规约

1. 通道 = 平台 + 设备 + 账号 + 配送点位 + 入口 + App 版本 + 控件集。通道是调度与并行的最小单位。
2. 同一通道串行、同一账号串行；不同通道可并行。跨城/跨商圈必须新增通道，不能靠改单条来源的 point 复用。
3. 一次提交生成一个比较组和三条平台任务，共享组 id、组截止与交付状态。
4. 平台适配器独立维护，共享契约与存储；京东已校准的控件、文字与比例不得直接套到竞对。
5. 跨平台比较前置：同实体门店、同单品规格与数量、同点位与账号条件、观察时差 ≤5 分钟。任一不满足只保留证据，不进入可比结论。
6. 组交付状态：`delivered`（三平台全部终止）、`partial`（部分完成或失败）、`blocked`（组级前置条件不满足）。partial 必须逐平台说明原因。

### 4.7 变更与基线规约

1. 改动适配器、页面地图、模型提示、几何支持矩阵、控件配置中的任何一项，都必须重跑对应层级的验收并更新基线。
2. 基线包含：应用版本、代码文件哈希、页面地图与本体版本、设备型号与系统版本、App 版本、模型型号与版本、支持矩阵。旧基线的结论不继承到新版本。
3. 冻结基线时同时冻结批次报告与证据索引，不删除失败批次。
4. 新增平台或新增城市/商圈时，先登记来源与通道，再做页面样本与校准，最后才进入验收。

### 4.8 数据与证据规约

继承 [数据治理表](../数据治理/数据治理表.md)：金额以分保存、未知留空并有原因、实测与推算分离、证据可追溯、来源条件与用途登记。新增要求：

1. 证据元数据必须含设备几何（型号、分辨率、density、方向、font_scale）与截图尺寸。
2. 通道信息（平台、设备、账号代号、点位简称、入口、App 版本）随任务保存，历史任务不被新通道静默改写。
3. 三平台同一组的观测保留各自 observed_at 与时差；不因并行而声称同秒。

## 5. 目标架构

```text
BD 提交（城/区县/品牌/分店/商品/规格/数量）
  → 生成比较组 + 三条平台任务（各绑定一个通道）
  → 单进程协调器（进程锁 + 调度轮询）
  → 通道池：{平台, 设备序列号, 账号, 点位, 入口, App 版本, 控件集, 几何档案}
  → 每通道一个 worker（同通道串行、同账号串行、跨通道并行）
  → 采集：设备自检 → 门店核对 → 商品规格 → 加购 → 结算 → 字段核对 → 恢复 → 证据落库
  → 组聚合：三平台状态、交付时间、partial 原因
  → 交付：报价、费用明细、证据、失败原因、性能与质量指标
```

与现有代码的对应：

| 能力 | 复用 | 改造 |
|---|---|---|
| 通道 | 现有 `AndroidSource` 的控件与字段结构 | 增加通道 id、允许同平台多条、按通道装配采集器 |
| 调度 | 现有 `Scheduler` 轮询与 worker map | worker 键改为通道，`claim` 增加通道条件与优先级 |
| 任务 | 现有任务契约与比较组 | 增加 `channel_ref`、组截止、取消接口，解除 specified 仅京东限制 |
| 设备锁 | 现有 locks 表与账号/设备互斥 | 增加 TTL、心跳、代号与回收 |
| 结果 | 现有 runDetails 与 comparisonRows | 增加组级交付状态与交付时延 |
| 证据 | 现有 EvidenceStore | 增加设备几何与截图尺寸元数据 |
| 值守 | 现有 `/api/devices` 与预检脚本 | 增加健康接口、告警、恢复接口与守护脚本 |

## 7. 资源与决策清单

| 事项 | 最低 | 推荐 | 说明 |
|---|---|---|---|
| 京东设备 | 1 台 | 2 台（1 主 1 备） | 当前唯一已打通链路，故障影响最大 |
| 美团设备 | 1 台 | 1–2 台 | 每平台 1 条通道才能并行 |
| 淘宝闪购设备 | 1 台 | 1–2 台 | 需先满足许可前置 |
| 备用机 | 0 | 1 台共享 | 锁屏/掉线/验证码时换设备继续 |
| 账号 | 每平台 1 个已核实测试账号 | 每平台 2 个 | 同账号串行，不同账号可并行但需分别核对资格 |
| 配送点位 | 每城 1 个已核实点位 | 按城/商圈多个 | 跨城需要新通道 |
| 专用机设置 | 必须：无锁屏、充电保持唤醒、关自动更新、固定竖屏 | 全部按值守规约 | 不设置则锁屏无法无人值守 |
| 120 秒口径 | 必须定义：提交到组交付 | 提交到组交付并单列排队 | 现状冷启动 124.3 秒 |
| partial 交付 | 需明确是否接受 | 接受两平台成功 + 一平台明确 blocked | 否则一个平台受限会拖垮整组 |
| 正确性样本 | 150 次全对（阶段） | 500 次累计错误 ≤10（最终） | 人工复核约 4–5 小时，可分次 |
| 告警渠道 | 本地日志 + webhook | 企业微信/钉钉/邮件 | 锁屏、验证码、掉线都需要人处理 |
| 淘宝闪购许可 | 书面许可 | — | 未满足前只能离线适配，不登记为已接通 |

## 8. 风险台账

| 风险 | 影响 | 应对 |
|---|---|---|
| 京东提速不达标 | 120 秒目标无法成立 | M2 先做；不达标则上调时延目标或增加热启动策略，不隐瞒 |
| 大促期页面动画导致读屏失效 | 京东 App 首页/详情页 uiautomator dump 等不到空闲而超时（桌面 2.4 秒正常、京东页面 11.8 秒超时，回滚基线仍复现） | 采集在 11.11 活动期（约到 11-12）不作为稳定验收窗口；活动结束后按同一基线重跑 20 次再判；替代读屏通道另行验证，见 27 号记录 |
| 第二机型布局差异 | 换机即 blocked | M1 几何门禁 + 比例参数化 + 双机验收 |
| OEM ROM 锁屏判定差异 | 无人值守静默停摆 | 任务前自检 + 告警 + 失败分类；未知状态一律告警 |
| 美团风控/账号受限 | 采集中断 | 低频、单账号、登记用途；受限即停止不换号 |
| 淘宝闪购无许可 | 平台无法上线 | 只做离线适配；许可未满足不纳入交付承诺 |
| 本地模型并发瓶颈 | 三平台并行时长尾叠加 | 模型网关并发上限与超时预算；必要时独立实例 |
| 单进程/SQLite 承载上限 | 设备数增加后吞吐受限 | 先做通道化；超过单进程能力再拆 worker 或迁移 |
| 正确性样本与人工复核成本 | 98% 结论迟迟不能发布 | 分阶段验收：150 次全对先给阶段结论，500 次给最终结论 |
| 设备与人力成本 | 多机多账号投入 | 分阶段扩设备：先 2 台（京东 + 备用），再接一个竞对 |

## 9. 立即执行的第一步

下一轮开发从 M1 的 P0 项开始，顺序固定：

1. 设备几何档案与门禁（记录型号、分辨率、density、方向、font_scale，超矩阵阻断）。
2. 京东搜索页去固定裁剪，统一图片点 → 逻辑坐标换算。
3. 商家标签与结果头部改控件相对布局，比例阈值进配置。
4. 证据隐私遮罩改节点驱动。
5. 参数化单测矩阵与静态门禁。

完成后再安排第二台真机做 M1 验收；M1 通过后进入 M2 提速，不跳步。

# 采集技术路线第一性原理复核：从设备 GUI 到浏览器 Web

版本 1.0，2026-11-08。针对「当前真机 GUI 自动化效率低、要专机、要无锁屏，是否有颠覆性替代路线」的问题，做第一性原理拆解、本机实测和公开项目考证。本文结论只到技术可行性与效率判断；合规判断单列，未把技术可行写成合规可行。

## 一页读懂

**有替代路线，而且提升是数量级的：把采集从「手机 GUI 自动化」迁到「浏览器 Web 自动化」。** 本机实测确认京东外卖网页端（`hour.jd.com`）与淘宝闪购网页端（`h5.ele.me`）都可正常加载；公开项目已分别跑通到「提交订单页」和「确认订单页」并读回全部金额。这条路不需要手机、不需要 USB、不需要无锁屏、不需要值守，一台服务器可并行多个浏览器会话。

**美团是例外。** 美团外卖 H5 的登录态接口对账号返回 403（响应头 `X-Forbid-Code`，账号级限制），多个公开项目均卡在这里，只能匿名看列表。美团大概率仍需设备路线，但只需一台（可云手机或模拟器），不再是三台专机。

**「Playwright 太慢」是误判。** 慢的不是 Playwright，是「ADB + uiautomator dump + 视觉模型」这套设备层方案：单次 UI 树读取 3.63 秒、一次采价 26 次读取、占 79.5% 耗时。Playwright 操作浏览器 DOM 是毫秒级，用在 H5 上反而最快。

**合规没有消失。** Web 自动化仍然是程序化访问，同样受平台协议约束；淘宝闪购的书面许可要求、美团的程序化访问限制都不因换技术栈而改变。独立合规调研的结论是四条候选路线没有一条「已合规」，Web 与真机同性质、只是被识别得更快。技术路线能降的是设备与维护成本，不是授权门槛。

**需求可以重排。** 三平台不必都用同一套采集：京东长期走内部数据，淘宝闪购走 Web，只有美团保留一台设备。设备与锁屏约束从「三平台各一台专机」压缩到「一个平台一台」。

## 1. 第一性原理：数据在哪一层，效率就在哪一层

外卖数据从平台服务端产生，经过接口层、渲染层，最后到达用户屏幕。可介入的层决定了效率上限与约束条件。

| 介入层 | 典型手段 | 单次耗时量级 | 约束 | 本项目可用性 |
|---|---|---|---|---|
| 服务端接口 | 官方 API、开放平台 | 毫秒级 | 需授权；本项目拿不到 | 排除（用户明确约束） |
| 页面内接口 | 逆向签名直调（美团 mtgsig、京东 h5st） | 毫秒级 | 需绕过签名/风控，平台会封；本项目规范禁止 | 排除 |
| **浏览器渲染层** | **Playwright 控制 H5 页面，读 DOM/截图** | **秒级** | 页面需登录；风控；协议限制 | **本次调研重点** |
| 设备渲染层 | ADB + uiautomator + 视觉模型（现状） | 分钟级（116 秒） | 专机、锁屏、USB、机型适配 | 当前方案 |
| 云手机/模拟器 | 云端 Android GUI 自动化 | 分钟级 | 仍是设备层；平台对模拟器风控更严 | 备选 |

结论：**在「拿不到 API、不做签名逆向」的前提下，浏览器渲染层是距离数据源最近的可用层。** 当前方案直接跳到最外层的设备 GUI，把「页面渲染 + 设备输入 + 屏幕读取」三份成本都背在身上，这是效率低的根本原因，而不是 Playwright 或某个库的问题。

## 2. 本机实测（2026-11-08，无头 Chromium，匿名访问）

| 入口 | HTTP | 加载耗时 | 页面状态 | 观察 |
|---|---|---|---|---|
| 京东外卖 `hour.jd.com` | 200 | 6.6 秒 | 标题「京东秒送」，显示外卖/超市/咖啡奶茶等分类，匿名可见商品与价格（49.9、59.9、66 元） | 22 个 XHR，含 `sgm-m.jd.com/h5/init`；个别静态资源 403，主体正常 |
| 淘宝闪购 `h5.ele.me` | 200 | 6.4 秒 | **跳转登录页**，标题「淘宝闪购-登录」 | 调用 `alsc-buy2.ele.me` 的 mtop 接口（页面自签名）；无 GPS 时定位报错 |
| 美团外卖 H5 `h5.waimai.meituan.com` | 200 | 10.5 秒 | 显示「您的网络好像不太给力，请稍后再试 / 重新加载」，商家列表未加载 | 检测到 `H5guard_BaseSec` 风控模块；两种 UA 与有头/无头都同样失败 |
| 美团官网 `www.meituan.com` | 200 | 6.4 秒 | 公司官网，非点餐入口 | 确认美团没有面向消费者的外卖 PC 点餐站 |

## 4. 效率对比

| 维度 | 当前真机 GUI | Web 浏览器（预估，待 POC 实测） | 倍数 |
|---|---|---|---|
| 单任务全链路 | 冷启动 116.7 秒 / 热启动 48.8 秒（实测 P50） | 页面加载 6–11 秒 + 操作若干步，预估 15–40 秒 | 3–8 倍 |
| 并发 | 1 台设备串行 | 一台服务器 10–20 个浏览器上下文 | 10–20 倍 |
| 吞吐（台/小时） | 约 30 次 | 数百到上千次 | 10–30 倍 |
| 硬件 | 4–5 台专用手机 + USB Hub | 一台服务器 | — |
| 值守 | 需保持唤醒、无锁屏、人工处理验证码 | 服务器常开；登录态过期时人工重登 | 大幅降低 |
| 机型适配 | 每机型重新校准（7–9 人日） | 无设备概念；只需适配浏览器与页面版本 | 消失 |
| 主要故障源 | 锁屏、掉线、控件变化、UI 树读取慢 | 登录失效、风控、页面改版 | — |

真机数据来自 20 次连续批次；Web 数据为页面加载实测加操作步数推断，**必须用 POC 实测替换，不能直接写进验收**。

### 4.1 设备层自身还有 3–5 倍提速空间

即使不换路线，真机方案也不是没有优化空间。独立调研证实：3.63 秒/次的根因是**每次读取都重启 uiautomator instrumentation**；改成常驻 instrumentation（uiautomator2 / Appium / 自建 server）后，单次读取实测降到 0.1–0.6 秒，10–20 倍。按本项目数据重算：报价 116.7 秒可降到 25–35 秒、结束 124.3 秒降到 30–45 秒、热启动 49 秒降到 10–20 秒；剩余约 25 秒是模型 7.8 秒、截图 3.5 秒、交互 13.7 秒。改造约 5–10 人日。

这也顺带解决「无锁屏」痛点：**插电并用 `svc power stayon true` 保持常亮即可避免进入 keyguard，不需要把设备设置成无锁屏**。设备仍需专用，但不必牺牲设备安全设置。

云手机方面：阿里云无影官方支持 ADB、Android 12、约 65–239 元/月（通用档 91 元）；腾讯云约 265–400 元/月；红手指 25–45 元/月。但云手机是机房 IP、无 SIM、虚拟传感器，平台风控识别概率中高；模拟器风控最高，不建议做主通道。若必须去设备，建议先用阿里云无影 91 元档 1 台做两周试点。

## 5. 三平台可行性分级

| 平台 | 等级 | 判断 | 依据 |
|---|---|---|---|
| 京东外卖 | **A：Web 可行** | 到提交订单页读全金额已被公开实现跑通；本机匿名首页可加载 | dsh-meituan + 本机实测 |
| 淘宝闪购（饿了么） | **B：Web 基本可行，待实测** | 登录到确认订单页的完整流程有公开验证；本机登录页可达；需真实账号与人工验证码 | ClawHub skill + 本机实测 |
| 美团外卖 | **C：Web 受限，需设备** | 登录态接口账号级 403，匿名列表受风控与定位限制；无 PC 点餐站 | dsh-meituan + 本机实测 |

由此，目标架构从「三平台各一台专机」变为「**两个平台 Web 并行 + 一个平台单设备**」。设备需求从 4–5 台降到 0–1 台，无锁屏、值守、机型适配问题只作用于美团一个平台。

### 5.1 三平台真实需求重排

把「是否需要采集」和「用什么采」分开看，结论比三平台一律采集更有利：

| 平台 | 是否必须采集 | 推荐获取方式 | 说明 |
|---|---|---|---|
| 京东 | 否（长期） | **内部数据导入** | 用户已确认可提供内部订单与商品数据；真机采集只是内部数据接入前的权宜验证 |
| 淘宝闪购 | 是 | **Web（Playwright）** | 饿了么 H5 完整流程已被公开验证到确认订单页 |
| 美团 | 是 | **单台设备（云手机/模拟器优先）** | 登录态接口账号级 403，Web 不可行 |

也就是说，最终形态可能只需要**一台设备采美团**，其余两条线分别走内部数据和浏览器。用户不想要的「专机、无锁屏」约束被压缩到原来三分之一以下的范围内。

### 5.2 官方智能体通道线索

合规调研发现淘宝闪购存在**官方智能体通道**（报道：支付宝与淘宝闪购 ACT，2026-01-16），说明平台已开放受控的第三方智能体接入路径。用户说「API 拿不到」，但如果该通道可申请，它会把淘宝闪购从「协议违约」变成「持牌接入」。这值得作为可选路径单独确认，不应默认排除。

## 6. 推荐重构方案

复用现有契约与存储，只替换执行器：

```text
提交（城/店/品）
  → 三平台任务（同组）
  → 执行器路由：京东、淘宝闪购 → BrowserCollector（Playwright 并发）
                  美团 → DeviceCollector（云手机/模拟器/真机，串行或轻并发）
  → 统一结果：报价、费用、证据（截图 + 页面快照）、失败原因
  → 组聚合与交付
```

阶段：
1. **POC（约 3 天）**：用 Playwright 在京东 `hour.jd.com` 与淘宝闪购 `h5.ele.me` 上，用已登记测试账号跑通「登录 → 选店 → 选品 → 加购 → 结算页 → 读金额 → 清空购物车」，记录单任务耗时、风控命中、登录态维持时长。首次登录的人工验证码不可避免。
2. **适配器改造（约 1–2 周）**：新增 `BrowserCollector`，实现现有 `Collector` 接口；证据改为截图 + DOM 快照 + 字段位置；复用现有契约、SQLite、比较与 UI。京东的 Taro 页面需要真实输入事件（`chrome.debugger`，与 dsh-meituan 同法）。
3. **美团设备路线**：Web 受限，保留设备采集。优先「普通真机 + 插电常亮（`svc power stayon true`）+ 常驻 instrumentation」，不需要无锁屏设置，也不需要专机级别的采购；单任务预计 30–45 秒。若一定要去设备，用阿里云无影 1 台试点两周（约 91 元/月），遇验证码即停。模拟器风控最高，不作为主通道。
4. **混合调度**：Web 并发 + 设备串行；组级交付取最慢平台。预计三平台组交付从 120 秒级降到 40–70 秒级（待 POC）。

## 7. 合规与风控

独立合规调研（`.runtime/audit/compliance.md`，18 条证据台账，逐条标注「协议文本事实／司法案例事实／公开技术资料／推断」）的结论：

**四条路线在当前协议文本下没有一条是「已合规」的**，差别只在违约程度、被识别速度和是否触碰刑事红线：

| 路线 | 合规风险 | 被封风险 | 结论 |
|---|---|---|---|
| A 真机 GUI（现状） | 高：违反「机器模拟客户端／未经书面许可自动化获取」条款，属违约 | 中 | 风险最低，但仍属违约 |
| B Web H5 自动化 | 高：同 A；淘宝闪购声明明文把「搜索、浏览、获取信息」纳入书面许可范围 | 中高：IP、账号易被限速 | 与 A 同性质，效率更高 |
| C 云手机/模拟器 | 高：同 A，另叠加「伪装设备身份」认定 | 高：虚拟设备是重点识别对象 | 仅在美团单平台时考虑 |
| D 抓包 + 绕签名 | 最高：反法第十三条第三款、刑法 285 条判例参照 | 最高 | 项目规范已排除，不再讨论 |

三条红线（触碰即从违约升级为违法/犯罪）：不破解签名/验证码/人机校验；不使用他人账号、不共享 Cookie、不伪装身份；不做实质性替代或对外转售数据。

对本次路线选择的含义：

1. **技术栈不改变授权门槛。** Web 自动化与真机自动化在协议上同性质，不能因为「浏览器更像真人」就认为合规。
2. **不绕过风控。** 滑块、验证码、短信验证全部人工处理，不打码、不做指纹伪装、不轮换 IP——与项目现有规范一致。
3. **不做签名逆向。** 只读页面渲染结果和页面自己发出的请求，不构造签名调用私有接口。
4. **登录态与账号安全。** 测试账号专用、登录由指定人员完成、Cookie 只存本机、不共享账号。
5. **数据口径需对照。** H5 与 App 的优惠、会员、新老客资格可能不同，Web 结算价必须先与 App 结算价做对照实验。
6. **平台已在主动拒绝 GUI 自动化。** 公开报道显示豆包 SAEP 被 150+ 应用（含淘宝、美团）拒绝 GUI 自动化（2026-10-15），说明设备层路线的识别压力在上升，这也是 Web 路线值得评估的现实理由之一。

**需要用户决策的合规事项**：谁承担违约/侵权责任、有无法务书面意见；用谁的账号与手机号、员工是否书面同意；是否接受「遇验证码即停、不换号不换 IP」；交付边界是内部决策还是对外 SaaS；是否重新评估官方通道或持牌数据商。

## 8. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 京东/淘宝闪购页面改版 | 选择器失效 | 页面指纹检测 + 失败即停止；地图/选择器版本化 |
| 淘宝闪购登录风控（短信、滑块、异地） | 登录失败 | 人工登录一次、保持会话；会话失效告警 |
| 账号级限制（美团已出现） | Web 路线失效 | 美团保留设备；其他平台出现即回退设备 |
| 并发被识别（同一 IP 多会话） | 限流/封禁 | 控制并发、加间隔；必要时分散出口；需用户与环境评估 |
| 合规判断 | 项目风险 | 由用户/法务确认；技术不自行宣布合规 |
| POC 实测不达预期 | 效率结论推翻 | POC 三天内给出实测，不达标就保留设备路线 |

## 9. 需要用户决策

1. **是否批准 Web 路线 POC**：需要淘宝闪购一个已登记测试账号（京东外卖若也要测，另需一个），首次登录由人工完成短信验证码。POC 只做技术验证，不进入生产采集。
2. **京东是否改为内部数据导入**：如果内部数据可在近期接入，京东这条线不需要 Web 也不需要设备，设备需求进一步降到一台。
3. **合规责任**：明知协议禁止仍采集，违约/侵权责任由公司还是项目承担；有无书面法务意见。项目规范不能替用户宣布合规，技术调研也不能。
4. **账号与个人信息**：用谁的手机号注册、员工是否书面同意公司使用其账号与位置信息。
5. **硬约束**：是否接受「遇验证码/风控/登录失效一律停止，不换号、不换 IP、不重试」；这会压低有效产出。
6. **交付边界**：结果只用于京东内部补贴决策，还是进入 SaaS 对外；后者会把「实质性替代/转售」风险抬高一个量级。
7. **官方通道是否重启评估**：淘宝闪购已有官方智能体通道（支付宝×淘宝闪购 ACT，2026-01-16 报道），美团有开放平台与服务商准入；用户说「API 拿不到」时是否需要再确认一次能否申请。
8. **若 POC 成功**，是否把 24 号计划的 M1（跨机型）与 M2（京东提速）替换为 Web 迁移；跨机型改造只保留给美团那一台设备。
9. **并发与出口**：Web 并发上限、网络出口是否需要企业网络或固定 IP。

## 12. 2026-11-09 常驻读屏实测结论（设备层提速的边界）

按 26 号研判落地"设备层常驻读屏"，实测结果如下，直接影响技术路线：

| 方案 | 单次读取 | 能读京东搜索页 | 能读门店页（小程序 WebView） | 能否常驻 |
|---|---|---|---|---|
| uiautomator dump（现状） | 2.7 秒 | 能 | **能**（111KB XML，含商家/购物车等文本） | 每次启动，无法常驻 |
| uiautomator2 server（u2.jar） | 0.14–0.28 秒 | 能 | **不能**（只返回 WebView 容器，31 个节点，无内部文本） | 能，app_process 常驻 |
| Appium uiautomator2 server | `/source` 约 0.6 秒 | 未验证 | 未验证（server 由 instrumentation 启动，测试方法结束后进程退出，未解决常驻） | 未解决 |

原因：京东外卖门店页是京东小程序（`MantoLightActivity` + WebView 渲染），门店、商品、购物车都在 WebView 的虚拟节点里。`uiautomator dump` 使用 AndroidX UiAutomator 的层级遍历，能拿到 WebView 虚拟节点；u2 server 的 `dumpWindowHierarchy` 只遍历 Accessibility 窗口树，WebView 内部节点不可见。这不是参数问题（已试 compressed/raw、maxDepth 50/200、rootInActiveWindow true/false，结果一致）。

由此得出的结论：

1. **常驻读屏路线在京东核心页面不可行**，不能作为主线；u2 只适用于搜索页等原生页面。
2. 设备层提速必须回到 **uiautomator dump 本身**：减少读取次数、合并 adb 调用、减少冗余强制刷新。预估单任务从 116 秒压到 60–80 秒，达不到原先 30–45 秒的预期。
3. 之前的 3–5 倍提速预估（26 号）不成立，需按实测修正；Web 路线的相对优势因此变大（京东/淘宝闪购 Web 端能直接读 DOM，没有 WebView 无障碍限制）。
4. 附带发现：多次启动/终止 instrumentation 会在手机上残留 `UiAutomation already registered` 僵尸连接，导致后续 dump 失败，只能重启手机清理；因此任何"混用多种读屏服务"的方案都要把重启成本算进去。

下一步：在 dump 链路内做读取次数优化（不改读屏服务），并用真机复测验证；同时保留 u2 作为"原生页面快读"的可选补充，但不进入主线。

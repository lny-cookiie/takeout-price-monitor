# 三平台外卖竞争监测

京东城市及品类运营可按城市、实体门店、商品规格、收货点位、账号资格和餐期查看报价。流程为京东资料导入、模型识别店品、人工确认映射、按监测条件采价、查看价差及证据。结算应付表示特定条件下的报价。历史实付单独保存。

## 实施契约

| 接口 | 输入与前置条件 | 输出与失败 |
|---|---|---|
| 京东订单导入 | 具备使用范围的最小字段 JSON。订单行键、门店和商品键使用字符串。去除账号、手机号和收货信息 | 分开记录历史实付与供给种子。同键重复导入不重复计数。缺地址、规格的种子待补 |
| 匹配建议与确认 | 选择目标及具体平台入口，提供有证据的候选。模型服务已配置 | 分别返回门店及商品的判断与缺项。只有满足硬约束并人工确认的版本可采价 |
| 监测计划 | 目标、资格、数量、收货点位、日期及餐期。真机任务需要已评估来源及设备配置 | 同组包含三平台计划槽位。缺映射、受限、超时和不可售均保留 |
| 比较与导出 | 按批次与业务维度查询。同一批次且观察时差在 5 分钟内才可比较 | 京东对每家竞对的金额差、可比原因、原始证据。超过 15 分钟显示历史；缺一路保留该列 |

## 技术选择与业务依据

保留 Node.js、TypeScript、SQLite。用 Midscene 和 ADB 做受控 Android 操作，以真实多模态 API 识别店品和页面。参考 Orderwise 多设备执行，结算取值单独实现。Orderwise 的正则解析会把缺失费用和起送未满足的总额写成零，已用独立输入复现。

- [美团场景建模](https://tech.meituan.com/2022/09/08/GNN-ScenarioModeling-SubgraphExtend-JointTraining.html)和[套餐组成](https://tech.meituan.com/2021/05/27/Set-Meal-Recommendation.html)用于确定点位、时段、用户和商品口径。
- [阿里业务说明](https://www.alibabagroup.com/en-US/document-2027233133950140416)和本地行业文章为经营效率提供背景。后续用京东出资、履约成本与复购核实经营收益。
- [Orderwise 源码](https://github.com/ucloud/orderwise-agent)与[小红书介绍](https://www.xiaohongshu.com/explore/69775b4100000000220303d2)展示多设备路线。[Midscene](https://github.com/web-infra-dev/midscene)、[Open-AutoGLM](https://github.com/zai-org/Open-AutoGLM)、[Mobilerun](https://github.com/droidrun/mobilerun)均有设备操作实现。
- [淘宝闪购访问规则](https://terms.alicdn.com/legal-agreement/terms/c_platform_service_agreement/20261008175730962/20261008175730962.html)要求第三方自动化接入前置书面许可。当前项目保持受限，待取得实际依据后复核具体入口。

## 实物商品比价材料复盘

已读用户提供的三张《估价自动化程序》截图，包括使用流程、基础采集接口、价格校验、导出格式与复盘。材料展示 Python、Selenium、线程池和表格导出。耗时和准确率是作者自报指标，截图没有提供可重复的样本及独立真值。

| 参考做法 | 外卖监测采用方式 |
|---|---|
| 执行前预览商品清单 | 京东资料导入时先核对门店、规格和实付，再生成目标 |
| 平台实现共享采集接口，互相隔离 | 各平台使用独立来源配置。调度器依赖统一接口，一端受限时保留其他端结果 |
| 分开登录状态、页面执行、价格处理及导出 | 测试账号留在设备，服务保存账号代号和资格依据。设备、模型、匹配、比较及 UI 分开 |
| 保留商品链接和采集时刻 | 导出包含观察时间、实际入口、映射和可访问证据链接。没有可靠商品链接时使用可定位的证据编号 |
| 校验搜索结果的异常低价 | 核对店品规格、点位、资格、优惠口径和同屏原值。外卖优惠可能真实形成低价，均值偏差不作为删除依据 |
| 平台并行及有限重试 | 多设备并行。同设备、同账号按锁串行。瞬时网络错误可有限重试，权限及页面变化明确失败 |

参考材料的浏览器 Cookie 文件不纳入实现。实物商品的榜首候选、固定优惠价和跨平台均价无法代替外卖的实体门店、套餐组成、用户资格及餐期。

## 模块职责

HTTP 层负责输入校验和路由。店品匹配与价差规则位于应用层。SQLite 保存目标、映射、条件、计划、尝试和报价。采集器依赖统一任务契约，Android 执行通过独立设备接口调用 Midscene。模型接口负责请求、输出校验与调用记录。切换模型地址通过配置，平台改版优先复核该入口的控件定义。

## 循环复核的技术结论

- **慢页面需要等待业务标志。**冷启动、搜索、规格、购物车和结算分别等待已核对控件，超时保留失败阶段。同一设备的检查和采集互斥。参考 [Android UI Automator](https://developer.android.com/training/testing/other-components/ui-automator) 及 [Appium UiAutomator2](https://github.com/appium/appium-uiautomator2-driver) 的状态等待和资源 ID 机制。
- **视觉定位与可控操作可以分工。**使用模型对脱敏页面定位，执行前核对设备、应用版本、控件和当前界面状态。查看了 [Midscene](https://github.com/web-infra-dev/midscene) 和 [Android 录制回放实现](https://github.com/oooooooko/android-midscene-automation) 的混合方法。项目保留同一 ADB 与 Midscene 运行路径。
- **名称相似用于找候选。**[DoorDash 的目录匹配经验](https://careersatdoordash.com/blog/augmenting-fuzzy-matching-with-human-review-to-maximize-precision-and-recall/)将模糊匹配与人工审核结合。本项目仍要求实体门店、规格和套餐组成证据，保存版本后复用。
- **门店新老客按店记录。**同账号在不同门店的资格可能不同。每条报价保存该门店与平台当时的资格、核对时间和有效期，条件缺失或过期时仍可看原始报价。
- **报价复核保留历史。**保存每次一致或不符判断、备注、时间和实际用时。不符的报价退出价差和最低价计算，原始报价与证据保留。

## 试点标准

一个城市选三店，每店两个比较对象，按同一已核实分层观察三天的午市、晚市、夜宵。三平台共 162 个计划槽位。核对门店、规格、结算金额与证据，记录不可售、受限、失败、可比样本、人工耗时及成本。代码、模拟回放、真实模型、真机和持续试点分别验收。

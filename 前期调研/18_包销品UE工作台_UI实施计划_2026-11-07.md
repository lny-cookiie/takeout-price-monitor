# 包销品 UE 工作台：UI 实施计划与验收

版本 1.3，2026-11-07。依据：16 号材料 v3.3。本版按内部包销品表口径同步。此文件先于实现建立；现已完成本地 UI 与验收，实测结果见第六节。

## 一页读懂

- **问题**：运营看到了单量和低价，却无法判断平台是否赚钱、商家能否持续供货，以及下一步该改什么。
- **使用者**：城市与品类运营、经营分析、财务及试点负责人。
- **使用过程**：先按城市、商圈、品类等范围看经营分组的平台 UE，再下钻问题商品和订单凭据；根据诊断建立动作，测算三种情景，通过约束后交给业务人工执行，最后核对结果。
- **本版范围**：可运行的本地 UI、统一的示例业务计算、六个页面及交互、业务约束、浏览器验收。全部金额和经营数据标注为示例数据。真实数据接入、生产身份权限、自动调价、自动补贴和平台后台操作不在本次 UI 交付内。
- **效果判断**：从经营分组能走到商品和订单证据；不成立的包销、比价、样本和执行条件会被程序拦截；页面数字能追溯到同一套计算。
- **当前状态**：六页 UI、业务计算和本地验证已完成；真实包销品表、财务与竞对接入、真实审批及经营效果仍待后续试点。

## 1. 页面与业务规则

| 页面 | 用户要判断什么 | 必须落到 UI 的规则 |
|---|---|---|
| 经营总览 | 哪些经营分组需要关注 | 平台 UE 主账；品类×城市×商圈×城市等级×用户×时段×流量入口；按订单量加权；连续四周基线；经营分组不足 100 单不作诊断；结果、驱动、约束指标分开 |
| 商品诊断 | 为什么亏损、证据是什么 | 补贴前后 UE；价格、补贴、成本、需求、供给履约五类原因；负 UE 且边际 ROI<1 才判补贴过度；30 单门槛；平台、商家、SKU 三本账；一单多品的分摊及尾差；按平台单均收益排序 |
| 策略测算 | 做哪个动作，最坏会怎样 | 价格/补贴/供给动作；负责人、期限、对象、证据；不动作、竞对跟价、仅老客三个反事实；乐观/基准/悲观订单、UE、利润、补贴、ROI；假设、版本、低置信度和回本说明；不通过不生成执行任务 |
| 执行任务 | 能否交给业务执行，如何退回 | 平台规则、预算、商家底线、同 SKU 活动冲突、人工审批、商家确认、发起方/出资方、七天告知期和退出记录；原值/目标值、执行前后凭据、操作人和时间；24 小时异常监控与人工回滚回填 |
| 效果复盘 | 做完是否改善、能否归因 | 实际和仿真比较；平台 UE、商家贡献、订单、GMV、补贴、ROI、复购、退款、差评、履约、毛利及价格指数；对照实验或准实验，前后对比不自动证明因果；保留/调整/停止回流动作库 |
| 数据管理 | 数据能否支持结论 | 包销范围只读核对；数据质量；指标说明：字典版本、完成订单分母、收支符号和成本归属、平台/商家/品牌资金分列、示例来源、缺失原因、对账和权限说明 |

**包销范围不再单独成页**。包销品表由业务维护，判定结果在数据进入主账前写入；工作台从数据表读取 `is_baoxiao`，在“数据管理 → 包销范围”只读展示每个商品是否计入包销及缺失原因，不提供登记、编辑或重判入口。业务人员不需要在 UI 重复登记。原“合同/有效周期”列已删除。

竞对比价嵌入商品诊断：同实体店、同品规格数量、同用户条件、同时间窗口和同履约方式；同时保留配送点位。时差不超过 5 分钟。任一不符只展示原始证据；零报价不能作为指数分母。结算应付、菜单标价、历史实付和商家结算分开。不同成交形态另作提示，不能由前端优惠倒推竞对平台出资。

## 2. 视觉和信息组织

沿用参考图的浅米色画布、白色内容区、暖灰表头、1px 边线和轻圆角。橘棕色只用于当前选择和主要动作；红色表示亏损或阻断，绿色表示通过，琥珀色表示待核实，蓝色表示中性信息。数字等宽并右对齐，单位放在表头或辅助文字中。

顶部横向导航，避免侧栏挤压宽表。筛选条是独立白色卡片，两行：第一行城市、商圈、城市等级、品类、流量入口、数据周期；第二行用户、时段、品牌（诊断/数据管理）、门店（诊断/数据管理）、搜索（诊断）和重置。筛选条在六个页面共用，切换城市会重置商圈和门店。

首页顺序为页面标题、筛选条、四项核心指标、经营状态矩阵、经营分组表。矩阵按新老客与午晚市排列，行是平台 UE 正值、补贴后亏损、补贴前亏损；点击格子筛选同一张表。样本不足单列，不放入成立的诊断结果。诊断页按平台单均收益从低到高排序，亏损商品优先。

详情使用右侧抽屉承载商品 → 订单 → 凭据，保持筛选上下文。宽表在自身容器内滚动；窄屏导航可横向滚动、筛选换行。键盘可操作，按钮有明确名称，空列表说明原因并提供清除筛选。

## 3. 输入与输出契约（实现前约定）

- **输入**：固定的本地示例包销品表、SKU、完成订单、费用、活动、竞对报价；金额存人民币分；未知值为 null；每个来源均为示例。以 2026-11-06 为演示截止日，四周为 10-10 至 11-06。
- **前置条件**：包销品表中 `is_baoxiao = true`。经营分组四周至少 100 单，SKU 四周至少 30 单。真实财务字典未确认，示例使用 `UE-V1-demo` 并显示这一状态。
- **输出**：按订单加权的三本账、缺失原因、诊断、可比结果、情景测算、带校验的本地任务及审计记录。
- **不变量**：未知不补零；结算后商家贡献不重复扣费；退款不缩减分母；示例与真实隔离；非包销不计入主账；订单成交形态不改变包销身份；同一份事实贯穿各页。
- **失败语义**：样本少则保留原始订单、抑制诊断和指数；缺成本则对应 UE 留空；比价不符保留报价并说明缺什么；任务校验失败显示具体原因并阻止流转；浏览器存储不可用时明确提示，不能伪装保存成功。

本地任务和复盘记录只保存在浏览器本地，重载可恢复。角色切换只演示界面和流程，不能作为生产权限控制。

## 4. 文案与信息密度规则

界面按奥卡姆剃刀处理：

- 不出现“演示/模拟/候选 SKU · 当前包销”“（演示分组）”“合同只展示脱敏摘要”“历史快照”等环境说明。
- 不出现面板标题后的“/ 12 条”“/ 20 条”计数、KPI 解释性脚注、表格尾注和假分页。
- 只保留顶部一处“示例数据”标识；数据来源说明放在“示例数据”抽屉。
- 业务状态和阻断原因必须保留：未取得、未接入、订单不足、成本缺失、不可比、未验证、未入池、预算不足、商家确认缺失、七天告知不足、活动冲突。
- SKU、GMV、ROI、UE、增量贡献、基线、样本等是运营和经营分析的通用词，保留原词，不改写成同义词。
- 只替换产品内部自造或实现层说法：历史快照→比价记录；主账/约束账/诊断账→平台每单赚多少/商家供货能否持续/商品收益；模型假设、测算版本→测算假设；假名化→用户身份去标识；null→未知。

“渠道”改叫“流量入口”。16 号材料的“渠道”指京东/美团/淘宝闪购，是跨平台维度；本工作台的平台损益主账只含京东订单，用“超级补贴/首页推荐/搜索进店”作为流量入口更准确，避免把竞对平台订单混进平台 UE。经营分组仍按品类×城市×商圈×城市等级×用户×时段×流量入口汇总。

## 5. 实施顺序

1. 写纯业务计算和示例数据：判定、金额、加权、分摊、诊断、比价、仿真、执行条件。
2. 完成六个页面，共用一套筛选、详情、指标和状态；把首页矩阵和业务表先做出来。
3. 接通从诊断到策略、仿真、模拟审批、人工回填、回滚和复盘的完整操作。
4. 增加本地 `/ue` 入口和独立预览命令。既有采集工作台继续保留。
5. 运行类型检查、业务边界测试、浏览器实际操作和截图检查；根据证据修复。
6. 更新项目规范、治理表、README、版本记录及本计划的验收结果。

## 6. 重点验收案例

| 场景 | 应有结果 |
|---|---|
| 直降品未入池，包销品用了券 | 前者非包销，后者仍为包销 |
| 同样单均 UE、订单量不同 | 汇总按实际订单量加权 |
| 原材料成本缺失；订单退款 | 商家贡献未知有原因；退款原单仍在分母 |
| 补贴前已亏；补贴后亏但 ROI 未知 | 前者结构问题；后者不能直接判补贴过度 |
| 竞对用户资格不同、超过 5 分钟、零金额 | 前两者不计算价差指数；零金额可有绝对差但不能除零 |
| 四周未满、SKU 少于 30、经营分组少于 100 | 不生成正式诊断或预测动作 |
| 仿真预算超限或商家底线未守住 | 不能生成任务 |
| 未审批、未满七天、活动冲突、发起出资不符 | 阻止执行并列明原因 |
| 回填执行和回滚 | 必填操作人、时间、前后凭据，保留审计历史 |
| 城市切北京、品类切饮品、商圈级联 | KPI、矩阵、分组表、诊断、策略商品、任务、复盘、数据管理同步变化 |
| 浏览器刷新、筛选为空、窄屏、键盘关闭抽屉 | 本地记录恢复；明确空态；页面无整体横向溢出；焦点返回触发处 |

## 7. 交付与验证记录

### 已交付

本地入口：[包销品 UE 工作台](http://127.0.0.1:4319/ue)。关闭服务后可双击根目录 `启动UE工作台.cmd`，或运行 `npm run build:ue`、`npm run dev:ue`。原服务更新后也提供 `/ue` 路由。

六个页面和以下交互均已落地：矩阵与筛选联动、经营分组 → 商品 → 订单凭据、包销品表二值标记读取、成交形态分组统计、同品五条件检查、多品逐分分摊、三情景仿真与反事实、人工任务、角色审批、执行回填、回滚、复盘回流、CSV 导出与本地刷新恢复。

示例输入为天津主样本（12 个经营分组、2 个虚构品牌、10 家虚构实体门店、24 个候选 SKU，其中 20 个 is_baoxiao=true），另加北京快餐、天津饮品、北京饮品三组各 4 个克隆 SKU，只用于验证城市、商圈、品类和流量入口筛选，不代表多城市试点。首页默认天津快餐的包销完成订单为 4,506 单；北京快餐为 858 单。食材成本缺失和少于 30 单的 SKU 保留为失败样例，不能被误当作已解决的数据问题。

金额与业务规则集中在 `src/domain/ue.ts`，筛选与级联在 `src/ue/scope.ts`，示例输入在 `src/ue/fixtures.ts`，界面与事件在 `src/ue/app.ts`，样式在 `public/ue.css`。页面没有接真实平台、财务或模型 API；浏览器状态与采集数据库分开。

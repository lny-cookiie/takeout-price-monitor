# 回归验证机制（用户级铁律，2026-11-10 定）

## 事故经过
2026-11-10 连续工作十余小时，三平台从"分别跑通"退化为"全部失败"。根因：在已跑通的核心文件上大改（jd-shelf-collector.ts 1974 行、android-transport.ts 418 行、android-collector.ts 313 行），每次失败改一处，累积破坏远大于修复。回退到 `9b603ce` 后京东立即恢复（101 秒跑通，amountFen 2160）。

## 铁律（不可违反）

### 1. 基线优先
- 任何改动前，先跑一遍当前基线并记录结果（commit hash + 耗时 + 业务字段）。
- 没有基线记录的改动一律不做。

### 2. 最小增量
- 已跑通的核心文件（`jd-shelf-collector.ts`、`android-collector.ts`、`android-transport.ts`、`android-uitree.ts`、`android-source.ts`）只允许**最小增量**改动（单个函数、单个条件）。
- 禁止重写、禁止大规模结构调整。

### 3. 改完必验
- 改一处 → 立即重跑同一基线 → 对比结果。
- 基线退化 → **立即 `git checkout <跑通commit> -- <文件>` 回退**，不允许"再改改看"。

### 4. 失败不叠加
- 同一个失败原因连续修两次没解决 → 停止，取证（dump/截图/日志），不允许盲改。
- 禁止在同一轮里改多个文件。

### 5. 只增不改
- 新增能力（美团、淘宝、调度、守卫）放在**新文件**里，不碰已跑通文件。
- 需要复用逻辑时，复制而非改造原文件。

## 执行流程（每次改动）

```
1. 记录基线：git rev-parse HEAD + 跑一次 + 存结果
2. 改（最小增量，单文件单点）
3. npm run check
4. 重跑基线
5. 对比：业务字段一致 & 耗时不退化 > 20% → 保留；否则 git checkout 回退
6. 只有通过 5 才 commit
```

## 禁止事项
- 禁止在未跑基线的情况下改代码
- 禁止一次改多个文件
- 禁止"失败后继续改同一处"超过两次
- 禁止把"记录诊断"当成"修复"
- 禁止用某次单跑成功冒充稳定性
